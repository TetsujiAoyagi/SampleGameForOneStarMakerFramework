# ワークフロー規則の導入理由（実測記録）

> この文書は規則を追加しない。規則の正本は各節に示す文書にある。規則を緩める・消すかを判断するときに、なぜ入れたかを確認するために読む。作業のたびに読む必要はない。

## HANDOFF を harvest して消す理由

手順（保存・引渡し確認 → harvest → 削除）の正本は [docs/README.md](../../../../docs/README.md) の「作業台」節。

- **harvest せずに放置すると、計画文書が 33 ファイル 13,300 行まで膨らんだ 2026-08 以前の状態に戻る**
- 判断に迷ったら基準は一つ: **次のスライスの実装者が知らないと事故るか。** 事故るなら `Docs/Architecture/` へ。事故らないなら git 履歴で足りる

## HANDOFF とアーキテクチャゲートの導入理由

正本は [handoff-template.md](handoff-template.md) と [architecture-gates.md](architecture-gates.md)。

2026-08 の SceneGraph スライスで `SceneGraphView.cs` は 368 行から 707 行（+92%、commit `33614c61`）に増え、レビュー修正後は 742 行（`79c68280`）になった。**当時の振り返りでは、原因は実装側ではなく HANDOFF の書き方**とされた。増える行数は書く前に見積もれたのに規模見積もりの欄が無く、変更対象ファイル一覧に黙って並べたことが、そのまま配置の指示になった。

**テスト要求は、構造の指示より強く効く。** `33614c61` では `SceneGraphClipboard.cs` と `SceneGraphPasteService.cs` が新規ファイルとして切り出され、どちらにもテスト（`SceneGraphClipboardTests.cs`、`SceneGraphPasteServiceTests.cs`）がある。当時の振り返りでは、HANDOFF がテストできる形を明示したことが切り出しを促したとされた。

同じスライスの Phase C で挙がった指摘 R1〜R5 は、当時の振り返りでは**全て機能バグで、設計指摘はゼロ**だった。受け入れ条件との照合だけを見ていたため。これが「構造レビューを機能レビューより先に行う」規則の理由である。

## セッションを切る理由 — コストはここで決まる

規則（Phase 境界では新しいセッションを使う）の正本は [phases-and-handoff.md](phases-and-handoff.md)。

2026-08-06 の SceneGraph スライスの実測（480 応答・実効 23.7M トークン）:

| 内訳 | 実効トークン | 割合 |
|---|---|---|
| 会話履歴の再読み込み | 11.7M | 50% |
| 新規に読み込んだ内容 | 6.6M | 28% |
| エージェント自身の出力 | 3.3M | 14% |
| 固定命令の再読み込み | 2.1M | 9% |

**うち約 58% がエージェント自身の発話に起因する**（生成 3.4M + それが以降の全ターンで再読される 10.4M）。序盤の長文ほど高くつく。1 応答あたり平均 1,401 トークンは長すぎた。

- **5 セッションに分割していれば約 -40%**（再読は分割数にほぼ反比例する）
- 外部エージェントへの実装委譲で浮いたのは 0.9%。**委譲はコスト対策にならない。効くのはセッションを切ることと応答を短くすること**
- 実装者を分けるのをやめる理由にはならない。むしろ分けるほど HANDOFF が育ち、セッションを切りやすくなる

**この事実は、常時読まれるファイル（`AGENTS.md`）を太らせないことにも同じく効く。**
