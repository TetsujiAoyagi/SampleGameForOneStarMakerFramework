# アーキテクチャゲート

## 基準

責務は行数やメソッド数ではなく、**独立して変わる理由**で数える。ファイルやクラスを分ける目的は小さく見せることではなく、依存、所有者、寿命、テスト境界、変更の波及を一致させることである。

`500行`、`3責務`、`1ファイル50%以上の増加`は構造レビューを発火させる警報として残す。閾値を超えたこと自体を分割理由にせず、分割または非分割の判断と根拠を HANDOFF に書く。閾値未満でも、独立した変更理由が混在するなら分割候補になる。

## Phase A: 責務マップ

新規または責務が増えるファイルごとに、次を HANDOFF へ書く。

- 責務を一文で表したもの
- そのファイルを変更する理由
- 状態と資源の所有者、寿命（App / Manual / Scene(id) / Bind(go) を含む）
- 許可する入力依存と出力依存
- Policy、orchestration、Unity / Editor I/O、永続化、表示のどれを担うか
- 公開 API と内部実装の境界
- 単体テストの対象と、Unity / `AssetDatabase` なしで検証できる範囲
- フォルダ、namespace、asmdef をその位置に選ぶ理由
- 予想行数。閾値を超える場合の分割または非分割理由

Phase A のアーキテクチャレビューは次を確認する。

1. 独立して変わる二つの判断が同じクラスに入っていないか。
2. Policy と Unity / Editor I/O、orchestration と中核ロジックが不必要に混ざっていないか。
3. Game → Framework、Runtime / Editor、asmdef の依存方向を曖昧にしていないか。
4. 状態の所有者と寿命が配置に一致しているか。
5. 新しい中核ロジックを単体テストできるか。テスト不能なら配置を見直したか。
6. 新しい公開 API、状態、依存 edge を必要最小限にできているか。
7. 将来一つの仕様を変えるとき、無関係な責務まで同時に触る構成になっていないか。

## フォルダとクラスの分割判断

フォルダ境界には、次のいずれかの違いを要求する。

- Framework / SampleGame
- Runtime / Editor
- Policy / infrastructure
- 公開 API / 内部実装
- 所有者または寿命
- 依存方向
- ドメイン語彙または変更主体

クラス数やファイル数だけを理由にフォルダを作らない。新しい汎用 `Helpers` / `Managers` / `Utils` を、未整理の判断を置く場所として作らない。既存名称を機械的に改名する規則ではなく、新しい責務の置き場を判断する規則である。

次のうち二つ以上が異なる場合は、分割に強い根拠がある。

- 変更理由
- 必要な依存
- 所有者または寿命
- テスト方法
- 再利用、差し替え、公開範囲

一方、同じ変更理由・依存・寿命・テスト方法を持つ凝集したアルゴリズム、宣言的な表、生成・足場コードは、大きくても非分割が妥当な場合がある。例外理由を記録し、行数を減らすためだけの委譲クラスを作らない。

## Phase B: 停止条件

実装中に次が判明したら、実装者は配置を独自に変更せず Phase A へ返す。

- HANDOFF にない状態、依存、所有者、寿命、公開 API が必要
- 計画したファイルへ置くと依存方向が逆転する
- 中核ロジックを単体テストするため責務分離が必要
- 別の変更理由を持つ処理を同じクラスへ追加する必要がある
- 便宜的な Helper / Manager へ設計判断を退避しないと進められない

## Phase C: 構造適合レビュー

機能レビューより先に次を行う。

1. Phase A の責務マップと実際のメンバーを照合し、計画外の責務を列挙する。
2. 実際の依存、所有者、寿命、公開 API、フォルダ、namespace、asmdef を計画と比較する。
3. 中核ロジックのテストが存在するかだけでなく、Unity なしで狙った単位をテストできる配置か確認する。
4. ある仕様変更を仮定し、無関係なメンバーやファイルまで変更が波及しないか確認する。
5. 行数警報が発火したファイルについて、`分割済み`、`非分割妥当`、`Phase A 再開`のいずれかと根拠を記録する。
6. 構造劣化が既存由来か、このスライスが作ったかを区別する。

Phase C は大きな再設計をその場で確定しない。責務マップの変更が必要なら Phase A を新しい revision として再開する。

## Phase C': 構造監査

C' は C の所見を見ず、隠れた第二責務、依存逆転、所有権の曖昧化、テスト不能な境界、過剰な公開面を探す。高リスク変更では、Phase A / B / C に関与していないモデル系列またはベンダーを優先する。
