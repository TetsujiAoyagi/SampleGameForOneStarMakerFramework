# Phase と HANDOFF

## Phase の責任

- **Phase A — 計画:** 受け入れ条件、変更対象、規模見積もり、設計上の制約、テスト方針を自己完結した HANDOFF にする。
- **Phase B — 実装:** HANDOFF の範囲だけを実装し、設計判断を増やさない。
- **Phase C — 一次レビュー:** 差分、構造、受け入れ条件、テスト結果を確認する。
- **Phase C' — 独立監査:** Phase C の結論を前提にせず、残存リスクと見落としを監査する。
- **Phase D — マージ判断:** 人間が結果を確認し、HANDOFF を harvest して削除する。

1スライスを1ブランチ、1 HANDOFFの単位とする。Phase境界では新しいセッションを使い、過去の会話ではなく HANDOFF、差分、テスト結果を入力にする。

## モデル選定と独立性

使用するモデル・サービスは固定しない。利用可能性、変更規模、専門性、コストを踏まえて各Phaseの開始時に選ぶ。

- Phase C は Phase B と異なるモデルで行う。
- Phase C' は Phase C と異なるモデルで行う。
- Phase C と C' は新規セッションで開始する。
- 可能なら Phase C' は異なるモデル系列または異なるベンダーを優先する。
- 条件を満たせない場合は独立レビュー・監査済みと扱わず、未実施として人間へ判断を返す。

使用した担当・モデルと独立性の充足状況を HANDOFF に実績として記録する。モデル名を将来の固定割り当てとして書かない。

## HANDOFF の必須内容

- 目的、対象外、受け入れ条件
- 変更対象ごとの現在行数、予想増分、責務
- 500行または3責務を超える見込みへの分割判断
- 新しい責務を置くファイルと、その配置を選んだ理由
- 新しい中核ロジックに対する単体テスト方針
- 実装上の制約をリンクではなく本文へ転記
- Phase Bの実装結果と未実行事項
- Phase Cの指摘、テスト結果、未確認事項
- Phase C'の監査結果
- 各Phaseで使用した担当とモデル

## 構造レビュー

1. `git diff --stat` を確認し、1ファイルが50%以上増えていれば責務分割を先に検討する。
2. 変更ファイルのメンバーを列挙し、意味が複数に分かれていないか確認する。
3. 新しい中核ロジックに単体テストが書けないなら、配置が誤っていないか確認する。
4. 構造的な劣化が既存由来か、この変更で生じたかを区別して記録する。
