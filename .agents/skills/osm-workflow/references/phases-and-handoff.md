# Phase と HANDOFF

## Phase の責任

- **Phase A — 計画:** 同じ planning packet から初稿、独立レビュー、人間による統合を行い、進める最低条件、その詳細である受け入れ条件、責務配置、規模、制約、テスト方針を自己完結した HANDOFF にして凍結する。
- **Phase B — 実装:** HANDOFF の範囲だけを実装し、設計判断を増やさない。
- **動作確認:** Phase B の完了 head で、検証経路の操作・実行時・目視の条件を各 1 回軽く実行し、実環境で成り立たない実装を発見 C より前に見つける（[動作確認](#動作確認phase-b-の後)）。
- **Phase C — 一次レビュー:** commit で固定した差分、Phase A の責務マップとの構造適合、進める最低条件、その詳細である受け入れ条件、テスト結果を確認する。**固定の対象:** 発見 C の差し戻し入力に限り、完全な変更集合を収録した stage snapshot（reference と packageSha256）で固定できる。判定 C と C' は commit 固定を必須とし、C / C' 用 bundle は同一 commit から生成する。snapshot を使うレビューでは、送信元の可変な作業ツリーをレビュー入力にしない。
- **Phase C' — 独立監査:** 発見 C と判定 C の結論と疑念候補を含まない blind audit bundle から、残存リスクと見落としを監査する。
- **Phase D — マージ判断:** 人間が結果を確認し、[Evidenceの保存・引渡し](review-evidence.md#phase-d-の保存引渡し確認) を確認してからHANDOFFをharvest・削除し、通常の終了処理と依頼範囲の後始末を行う。元証拠の保全だけを後始末完了としない。

未移行作業は1スライスを1ブランチ、1 HANDOFFの単位とする。A3で `external-current-v1` を採用したArtifacts/Harness作業は、同じ単位の現行入力をGit外CURRENTで選択する。`pwsh tools/harness.ps1 current -Task <id>` が入口で、凍結仕様とrunはIDから解決する。CURRENT管理方式の移行を明示していない作業に、この管理方式を暗黙適用しない。Evidenceの保存・引渡しはH1採否と独立して [レビュー証拠](review-evidence.md#保存先とリモートへの配布) に従う。Phase境界では新しいセッションを使い、過去の会話ではなく各Phaseの固定入力を使う。

通常の task 全体完了・打切りは人間の決定を処理する同じ最終手順で tools/workflow-task.ps1 end に接続する。Phase D の完了処理も対象とし、C/C′ 合格や Harness close を終了へ変換しない。再開は Evidence 利用前に resume を完了する。終了指示 record／event／receipt の途中失敗は同じ Decision・内容で回復し、確定済み終了 UTC を変更しない。新しい承認を増やす規則ではなく、既存の完了・再開手順の記録入口である。詳細は [Workflow README](../../../../tools/Workflow/README.md)。
## Phase A の内部フロー

1. **A0 — 入力固定:** 現況、要求、対象外、常時契約、既知の制約、未決事項を planning packet にする。
2. **A1 — 初稿:** 主担当が進める最低条件、その詳細である受け入れ条件、責務マップ、配置、規模、テスト方針、停止規則を含む初稿を作る。
3. **A2 — 独立レビュー:** 同じ入力版を複数モデルが独立に見る。互いの指摘を渡さず、観点を分ける。少なくとも1件は [アーキテクチャゲート](architecture-gates.md) を担当する。入力版は内容の sha256 を正とし、commit hash を補助として記録する。
4. **A3 — 統合と凍結:** 主担当と人間が指摘を採用・不採用・保留に分類して理由を残し、実装へ渡す版を凍結する。

通常スライスは主担当と1件以上の独立レビュー、高リスクスライスは複数の独立レビューを使う。高リスクでは、初稿にアンカリングされないよう、A0 だけを読んで代替構成を出す担当を少なくとも1件検討する。

高リスクの例は、公開 API、依存・asmdef、所有者・寿命、`SceneState`、Addressables、並行処理、破壊的な生成器や移行を変えるスライスである。レビュー数を増やすこと自体を目的にせず、観点と独立性を割り当てる。

高リスクの初回実機スライスで独立して失敗しうる未知が複数あるなら、A0 / A1 で問いを分け、後続の問いと所有スライスを記録する。起動・stripping・fixture 合成・配布形診断などを一つの最低条件に束ねる前に、それぞれの成立を別に判定できるか確認する。分割先の実装は、そのスライスの着手時に行う。

A2 の指摘は全件採用を既定にせず、現在の問い、最低条件、常時契約との関係で採否を決める。所有者・API・寿命等の契約違反は解消し、証拠スキーマや診断項目の追加は現在の問いの判定に必要なものに限る。

## 検証経路の成立

操作・実行時・目視を伴う最低条件は、A1 で条件ごとに次を短く書き、A2 で実行可能性、A3 で担当と証拠の受け入れ方を確認する。既存のテストで閉じる条件はテスト名の参照でよく、別の大きな帳票を作らない。

- 誰が、どの環境・初期状態から、何を操作するか。
- 何を観測すれば合否を判断できるか。構造・値の検査と、画像で判断する見た目を区別する。
- 保存する証拠と取得対象の版、C / C' がその証拠を読める受け渡し方法。

未知の操作経路だけは、凍結前に接続、必要コマンド、対象状態への到達・観測・保存が可能かを小さく確認する。接続成功だけをゲーム内の移動や再入場の成功と扱わない。未実装機能そのものの成功は求めず、既存経路の疎通と未実装の検証支援を区別する。Unity テスト・Build が必要な試行は Phase C の担当へ渡す。その場合は「未確認。初回確認は Phase C」と理由・担当・確認地点を記録し、不成立時の基盤整備または問いの分離も A3 で合意して凍結する。未確認を疎通成功や `なし` に読み替えない。既知の経路を全件再実行するゲートにはしない。

経路が成立しない場合は、必要最小限の操作・観測支援を実装計画へ含めるか、先行して検証基盤を整えるか、問いを分ける。支援を同じスライスで作るなら、必要な権限・依存と疎通を確認する地点も決める。「AI ができなければ人間が歩いて見る」を既定の代替手段にしない。人間が実装を担当する合意も、検証の代行・反復まで一括して引き受けた意味にはしない。

美観・遊び心地など人間の判断が必要な条件は、人間が担当することを明示して合意する。その場合も AI が可能な起動・場面準備・撮影・記録は AI が行い、人間へ求める判断を限定する。人間の観察記録を受理するのか、監査担当自身が画像を再評価できることまで必要かを凍結時に区別する。後者なら撮影条件と保存画像を必須とし、前者でも対象版・場面・観察者・結果を記録する。lightmap の割当だけで seam が無いと証明したり、画像だけで unload 完了を証明したりしない。

凍結後に経路の不成立が判明した場合も、まず基盤不備・観測不足・実装欠陥を区別して記録する。権限内で解消できる基盤不備は担当 AI が直し、契約・責務・受け入れ条件を変える必要がある場合は既存の「新しい事実の分類」に従う。未検証を成功へ読み替えず、条件の除外を AI だけで決めず、人間への確認依頼を反復して穴埋めしない。

検証経路は、下記の動作確認の実行担当がそのまま実行できる粒度（コマンド、引数の作り方、事前・事後に観測するもの）で書く。

## 動作確認（Phase B の後）

Phase B の完了 head で、検証経路に書いた条件のうち offline のテストで閉じないもの（操作・実行時・目視の条件）を、発見 C より前に各 1 回、軽く実行する。目的は、実環境で成り立たない実装を判定の直前ではなく実装の直後に見つけることである。合否の判定や GO の証拠の代わりではない。

- **対象外:** テスト suite、Unity バッチテスト、Build、高コスト証拠。これらは従来どおり Phase C と最終証拠ラウンドが担当する。Unity テスト・Build を要する条件は、ここで実行しない。
- **担当:** 検証経路で条件ごとに決めた実行担当。B の session が実行できる条件は、B が出口で行ってよい。別の環境が要る条件（例: 仮想化された host 内の実行）は、その環境の実行担当が行う。実行担当は検証経路の手順だけを実行し、対象 head、コマンド、生の出力、事前・事後の観測と、検証経路の期待との差の有無を残す。GO / NO-GO と合否は書かない。差を見て B へ戻すのも実行担当である。想定外の結果が出ても、原因調査や再実行で埋めない。
- **結果の扱い:** 検証経路の期待と違う観測があれば、発見 C を待たずに B へ戻す。この往復は、B と発見 C の差し戻しの巡（SKILL の 1 巡の定義、上限 4 巡）に数える。最初の動作確認は数えない。実行担当を用意できない条件は、理由と担当を記録して `未実施` とする。発見 C は開始してよいが、`未実施` は判定 C を完了と記録する前に解消する（取得は判定 C の担当が行ってよい）。未実施が無ければ `なし`、検証経路に該当する条件が無いスライスだけ `対象なし` と記録し、`対象なし` 以外は判定 C のゲート対象である。
- **出口:** 動作確認の担当は、最後の手順として HANDOFF の引継ぎ票（PR が存在する間は PR の状態ブロックも）を次の担当（発見 C、差し戻しなら B）へ更新する。
- **判定 C との関係:** 判定 C は GO 候補 head で同じ条件の証拠を揃える。動作確認の対象 head が GO 候補 head と同じで、B 以外の実行担当が取った生の観測なら、判定 C はそれを判定の入力にしてよい。B の session が取った観測は判定の入力にしない（[実行担当と判断担当](#実行担当と判断担当)）。

## 意思決定境界とスコープ停止

各スライスは A0 から A3 までに、次の意思決定境界を本文へ固定する。

- **このスライスが答える問い:** 次スライスの候補として扱ってよいかを判定できる、一つの問いにする。
- **進める最低条件:** GO に必要な証拠だけを列挙する。スパイクで CONDITIONAL ACCEPT を使う場合は、その判定に必要な証拠も列挙する。
- **受け入れ条件:** 進める最低条件を構成する観測可能な詳細とする。別の完了バーを作らない。
- **発見用テストと判定必須テスト:** Phase A は差し戻し中の確認に使う起点 filter と、GO 候補 head の判定必須テストを本文で分ける。実装変更を伴うスライスでは最終の全 EditMode 回帰を判定必須の標準とする。適用除外は理由と代替証拠を書く。起点 filter は固定リストではなく、C が凍結済み条件の確認に必要な範囲を根拠付きで変えてよい。受け入れ条件の追加とは区別する。
- **ここでは答えない問い:** 所有する後続スライスの HANDOFF または program 名を項目ごとに明記する。
- **停止規則:** 進める最低条件を満たし、現在の問いに致命的な反証がなければ終了する。最低条件未達のまま終了しない。スパイクに限り、HANDOFF 本文で判定基準を定義した CONDITIONAL ACCEPT を正常な成功判定として扱える。

### 不変条件と成立条件

本規則の導入後に新しく A1 を始めるスライスから適用する。導入時点で A1 を始めていたスライスは書き直さない。

- 進める最低条件を、**不変条件**（起きてはいけないこと。例: 候補でない Build を消さない、確認できない削除を削除済みにしない）と **成立条件**（起きなければならないこと。例: 上限を超えた最古の Build が削除される）に分けて先に書く。どちらも観測可能な語で書く。
- 受け入れ条件は各条件の検証例として書き、検証する条件を紐付ける。不変条件ごとに、失敗経路を含む受け入れ条件を少なくとも1つ持つ。
- A2 では、各不変条件を破る順序を1つ挙げられるかを確かめる。時点・終了境界・条件間の優先関係が曖昧な受け入れ条件には合格例・不合格例を付けて読み違いを探す。例は条件の代替にしない。

A3 でこの境界を凍結した後、finding が現スライスを阻害できるのは、凍結済みの進める最低条件、受け入れ条件、または `AGENTS.md` 等の常時契約への違反を示す場合だけである。blocker には違反する条件または契約を明記する。それ以外の新しい不確実性は、重要度や失敗時の影響にかかわらず後続スライスへ送る。「知れたら有益」「将来必要」「証拠が完全になる」は追加理由にならない。

### blocker の基準

Phase C / C' の blocker は、違反する条件または契約と、その一次証拠を記録する。不変条件を実行時に破る指摘には、加えて違反に至る具体的な順序（入力・状態・操作の列）を記録する。成立条件の不成立、受け入れ条件の失敗、静的な契約違反、必須証拠の欠落は、失敗した条件と一次証拠で足りる。受け入れ条件の文言の隙間で、どの凍結済み条件・常時契約にも違反しないものは blocker にせず、決定記録での読み方の確定か後続スライスの入力にする。

### 決定記録

A3 後に人間が下す裁定のうち、凍結条件の意味・合否を変えないもの（指摘の不採用、後続スライスへの移送、どの条件の合否も変えない受け入れ条件の読み方の確定）は、結論と理由を **決定記録** に残す。決定記録は Phase A snapshot に追記せず、版と適用時点を持つ別の記録にする。凍結条件の意味・合否を変える裁定は決定記録で行わず、Phase A を新しい revision として再開する。受け入れ条件・成立条件の合否が変わる読みもこれに含める。C' に渡す範囲は [レビュー証拠](review-evidence.md#c-用決定記録) に従う。

追加検証を提案するときは、まず `凍結済みのどの条件または常時契約への違反を判定するか` を確認する。

- 根拠を示せるなら、凍結済み条件の確認として現スライスで扱う。
- 根拠を示せない新しい不確実性は、重要度にかかわらず所有する後続スライスへ送る。
- 現スライスへ例外的に取り込む必要がある場合は、人間が例外として明示承認し、置き換える既存条件、または追加作業の期限・検証予算を指定する。承認後に Phase A を新しい revision として再開する。

レビュー担当は欠陥を指摘できるが、スコープを自動拡張しない。Phase C / C' の finding は「凍結済み条件または常時契約への違反により現在の問いを阻害する欠陥」と「後続スライスの入力」に分類し、前者には違反根拠を記録し、後者による追加実装を行わない。後続スライス名を付けた項目を現在のハーネスで検証し始めた場合は停止し、HANDOFF の境界と移送先を確認する。

## 新しい事実の分類

実装中または発見 C で新しい事実が出たら、Phase A を再開する前に次へ分類する。これは修正先を決める手順であり、レビューの「現在の問いを阻害する欠陥 / 後続スライスの入力」の二分類を置き換えない。

- **A 再開:** 凍結済み条件を満たすため、計画外の状態・依存（asmdef を含む）・所有者・寿命・公開 API、または失敗時に処理を拒否する契約（fail-closed）の変更が必要。計画した責務配置では条件を満たせない場合も含む。新しい revision で A2 / A3 を行う。受け入れ境界の拡張には、前節の人間による例外承認が必要。
- **B 適応:** 凍結済み A3 の許可範囲にある実装詳細や不具合修正で、上記の契約と責務配置を変えない。例えば、A3 が許可した実 Player で欠けた型だけの `link.xml`、任意としたスモーク検証の API 選択、既存の名前契約を満たす一時 Scene 複写。例に該当するだけで許可済みとはせず、今回の A3 と常時契約に照合する。根拠と変更を HANDOFF の実装結果へ簡潔に記録し、Phase A は再開しない。
- **スパイク:** 凍結済み条件に関わる失敗の原因が未確認。仮説を確定した設計として A3 に凍結せず、ログ・既存 filter・必要なら対象を絞った Player 検証で因果を確認してから、他の三つへ分類する。確認する条件、観測範囲、終了条件を記録し、Unity テスト・Build は Phase C が担当する。別のスパイクスライスや CONDITIONAL ACCEPT を自動的に追加する意味ではない。
- **後続スライス:** 凍結済み最低条件・受け入れ条件・常時契約への違反根拠を持たない新しい不確実性。所有する後続スライスへ送る。成功経路が動くことだけでは分類せず、凍結済みの失敗経路の契約違反も現在の欠陥として扱う。

「失敗した」「知らなかった」「証拠が薄い」だけでは A 再開しない。一方、B 適応でも欠陥修正と必要な再検証は省かない。完了して harvest 済みのスライスは、後続入力を残すためだけに再開しない。

## モデル選定と独立性

使用するモデル・サービスは固定しない。利用可能性、変更規模、専門性、コストを踏まえて各Phaseの開始時に選ぶ。

- Phase C は Phase B と異なるモデルで行う。
- Phase C' は人間または AI が担当する。AI が担当する場合は Phase B、C の両方と異なるモデルを使う。人間担当にモデルの相違条件は適用しない。
- Phase C と AI 担当の C' は新規セッションで開始する。
- **最低条件（AI担当）:** C' は B/C と異なるモデル、新規セッション、blind audit bundle を使う。満たせない場合は独立監査済みと扱わず、未実施として人間へ返す。
- **人間担当:** 同じ固定 base / head の blind audit bundle を確認し、所見、確認範囲、未確認範囲、残存リスク、判定を本人が明示する。AI は証拠準備と機械検査を補助できるが、人間の回答前に PASS や監査完了を記録しない。
- 人間が Phase C の結論を先に読んだ場合や設計・実装に関与した場合は、その事実を `独立性制約あり` と記録する。実施した人間レビューは記録できるが、盲検の独立監査済みとは記載しない。
- **強化条件:** 高リスク変更の C' は、可能なら Phase A、B、C に関与していないモデル系列またはベンダーを使う。Phase A で利用可能な全系統を使い切らず、監査担当を予約する。
- 強化条件だけを満たせない場合は監査自体を未実施にはしない。`独立性制約あり`として理由と残存リスクを HANDOFF に記録し、人間が採否を判断する。

使用した担当・モデルと独立性の充足状況を HANDOFF に実績として記録する。モデル名を将来の固定割り当てとして書かない。

人間担当の C' と Phase D は同じ人でもよい。C' は証拠に対する監査所見、D は C/C' の突合とマージ判断として別々に記録する。マージした事実だけを C' 完了の根拠にしない。大量生成物は全件の機械検査と代表箇所の目視・操作確認を組み合わせ、標本確認を全件目視済みと扱わない。

## Phase 境界の引継ぎ

### 引継ぎ票

各 Phase の出口の担当は、次の担当が会話履歴なしで始められるよう、HANDOFF §0 に引継ぎ票を書く。正本は HANDOFF §0 とする。

- 次の Phase と役割、次の作業。モデル名は書かない
- 凍結した Phase A の revision、implementation base / head、引き継ぐ commit SHA。stage を使う場合は取得案内の所在（reference と packageSha256 の実値は取得案内に置き、tracked HANDOFF と PR 本文には転記しない）
- 入力となる各 snapshot・bundle の取得案内の在処と状態
- 必要な権限（Unity、実操作、資格情報、sandbox 外実行）
- 停止規則と、引き渡さないもの（C' に所見を渡さない等）

### 実行担当と判断担当

判定 C の判断担当が判定必須テストや高コスト証拠を実行できない場合、B の session は実行を代行しない。判定 C 用に新しく開いた実行担当の session が凍結済みのコマンドだけを実行し、生結果を判断担当へ渡す。照合 script を代行実行する場合は [判定 C の照合 script](review-evidence.md#判定-c-の照合-script) の実行環境の条件に従う。実行担当も Phase C に属する。B の session は B の出口（commit し、引継ぎ票に SHA と取得案内の所在を書く。push は [公開点](../SKILL.md#公開点とgit履歴) の規則に従う）で終える。

### PR 状態ブロック

PR の本文先頭に、HANDOFF §0 の最小の写しとして状態ブロックを置く。項目は [テンプレート](handoff-template.md#pr-状態ブロック) に従い、reference・hash の実値は書かない。状態ブロックの更新義務は PR が存在する間に限る。PR を作る前は HANDOFF §0 を唯一の正本とする。

- タイトルはスライスの成果を表す名前にし、Phase を入れない。Phase は状態ブロックにだけ書く。
- 各 Phase の出口の担当が、その Phase の最後の手順として更新する（A3 凍結、B 完了、動作確認完了、判定 C 完了、C' 完了、D）。implementation head を固定した時点でも更新する。
- C' 完了まで、状態ブロックと本文に判定 C の結論・指摘を書かず、「判定 C 完了」の事実だけを書く。C / C' の結果は Phase D で本文に要約する。
- Phase D の担当はマージ前に、状態ブロックと本文の要約が最終 head と一致することを確認する。

引き継ぐ担当は開始時に、HANDOFF §0 の引継ぎ票の commit SHA と自分の worktree の HEAD を照合し、作業ツリーが dirty なら引き継がない。PR が存在する間は状態ブロックも照合する。同一 PC ではローカルの SHA で照合し、origin との照合は Cloud・別 host の担当が割り当てられている時だけ行う。食い違えば引き継がずに停止する。レビュー用の worktree は固定 SHA からの detached worktree でよく、同じブランチを複数の worktree で checkout する必要はない。C' は PR を入力にせず、所見を含まない C' 用の取得案内だけで始める（[レビュー証拠](review-evidence.md#保存先とリモートへの配布)）。

### Cloud の担当

Cloud は凍結入力を読む役（A2・C'）を既定とし、B の修正ループに入るのは例外とする。Cloud の担当が割り当てられた Phase 境界では、PR 作成、状態ブロックの更新、対象 SHA の push を必須の手順とする。Cloud のエージェントは、リモートのブランチの HANDOFF と PR の状態ブロックから、現在の Phase、固定 head、次の担当を判断する。PR の有無にかかわらず、必要な固定 Evidence を取得・検証・閲覧できない Cloud の作業は **assist** とし、正規の発見 C・判定 C・C' と扱わない。PR 作成や push だけで正規の担当に昇格させない。別 host / Cloud から Evidence を取得する仕組みが成立していない間は、状態ブロックには証拠の取得はローカル担当と書く。

## HANDOFF の必須内容

- type、status、branch、implementation base / head commit、risk、owner、期限、harvest 先
- 各 Phase の出口で書く引継ぎ票
- Phase A snapshot、Phase B result snapshot、evidence bundle、C' blind audit bundle それぞれの取得案内の引渡し先・担当・状態。公開欄と実際の取得案内の区別は下記に従う
- 目的、対象外、このスライスが答える問い、進める最低条件、その詳細である受け入れ条件、ここでは答えない問いと所有スライス、判定定義、停止規則
- A0 の現況、制約、未決事項
- 新規 A1 のスライスでは不変条件と成立条件、受け入れ条件との紐付け
- A3 後の決定記録の入口と状態
- 高コスト証拠の分類、取得手順、独立した期待値。判定 C の照合 script の方式
- Phase A の独立レビュー結果と採用・不採用・保留の理由
- 変更対象ごとの責務マップ、現在行数、予想増分
- 500行、3責務、または50%以上の増加が見込まれる箇所への分割または非分割判断
- 新しい責務を置くファイルと、その配置、依存、所有者、寿命、テスト境界を選んだ理由
- 新しい中核ロジックに対する単体テスト方針
- 差し戻し中の起点 filter と判定必須テスト。実装変更スライスでは最終全 EditMode 回帰が標準。適用除外の理由と代替証拠
- 実装上の制約をリンクではなく本文へ転記
- Phase Bの実装結果と未実行事項
- 動作確認の対象 head、条件ごとの実行担当・生の観測、期待との差と B への差し戻し、`未実施` / `なし` / `対象なし`
- Phase Cの種別（発見 / 判定）、使用したevidenceの取得案内・状態、構造適合、違反根拠を伴う現在の問いを阻害する指摘、後続スライスへ移送する指摘、実行したテストコマンド、テスト結果、判定必須のうち未実行、未確認事項
- Phase C'の種別（暫定 / 最終）、使用したblind audit bundleの取得案内・状態、違反根拠を伴う現在の問いを阻害する指摘、後続スライスへ移送する指摘、監査結果、独立性
- Phase DのEvidence保存・取得確認と取得案内の引渡し、task終了・後始末の状態、未完了事項。公開欄へ内部台帳や機微なpathを転記しない
- 各Phaseで使用した担当とモデル

tracked HANDOFFの全Phase欄には、既存の取得案内の引渡し先・担当と状態（未生成／未保存／ローカル固定済み（未昇格）／引渡し未完了／確認済み）を公開可能な範囲で記録する。reference・期待packageSha256の実値、ローカルpath、内部catalog/receiptを転記しない。実際の取得案内には [レビュー証拠](review-evidence.md#保存先とリモートへの配布) に従い、stage / publishが返すreferenceとそれとは別の期待packageSha256、対象base / head、用途、所在task、取得手順、保持条件、引渡し先、`locality` を残す。各snapshot・bundleの生成時刻と内容hashは固定manifestに残し、packageSha256と混同しない。同じpackageの取得案内は再利用でき、個別publishや第二の台帳を要求しない。C' 用の案内と入力は所見から分離し、空欄や生成済みだけを保存・引渡し済みと扱わない。

スライス HANDOFF は [テンプレート](handoff-template.md) を基準にする。複数スライス計画と調査記録は `type` を区別し、Phase C / C' の完了欄を持つスライスと同じものとして扱わない。

## 構造レビュー

詳細は [アーキテクチャゲート](architecture-gates.md) を正とする。

1. `git diff --stat` を確認する。500行、3責務、50%以上の増加は自動分割条件ではなく、構造判断の説明を要求するトリガーとする。
2. Phase A の責務マップと変更ファイルのメンバーを照合し、独立して変わる理由、依存、所有者、寿命、テスト方法が混在していないか確認する。
3. 新しい中核ロジックに単体テストが書けないなら、テスト不足だけでなく配置が誤っていないか確認する。
4. フォルダ、namespace、asmdef、Runtime / Editor、Game / Framework の境界が計画と一致するか確認する。
5. 構造的な劣化が既存由来か、この変更で生じたかを区別して記録する。

## レビュー証拠と C' の盲検性

詳細は [レビュー証拠と指摘記録](review-evidence.md) を正とする。

- 判定 C と C' は同じ implementation base / head commit と判定 evidence bundle を使う。C' が同じテストを重複実行することは必須にしない。高コスト証拠を分類したスライスの暫定 C' と最終 C' は [高コスト証拠と最終証拠ラウンド](review-evidence.md#高コスト証拠と最終証拠ラウンド) に従う。
- Phase C' に可変な HANDOFF 全文を渡さない。入力は所見を含まない blind audit bundle だけとし、構成と原記録の扱いは [レビュー証拠](review-evidence.md#phase-c-の-blind-audit-bundle) を正とする。
- 発見 C と判定 C の結論、指摘、疑念候補、誘導的な説明は C' 完了まで隔離する。B result へ発見 C の所見を転載しない。
- 判定 C と C' の所見は Phase D で初めて突き合わせる。
- 発見 C は C' を起動しない。テスト未実行でも構造・契約の ledger を返してよい。GO 判定はしない。
- レビュー対象の implementation head または対象 diff が変わった場合は [判定後の head 変更](review-evidence.md#判定後の-head-変更) に従う。
