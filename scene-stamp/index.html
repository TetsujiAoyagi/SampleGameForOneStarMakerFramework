Scene の印を source に残さず、prefab の編集を差分 build に効かせる

追記（2026-11-17）: 元の不具合は Unity 6000.6.9f1 で直っていました（前の記事の追記を参照）。6000.6.9f1 以降なら、この記事の印の方式は要らない見込みです。入れ子の prefab では 6000.6.9f1 でまだ確かめていません。以下は 6000.6.0f1 での記録です。

前の記事で、prefab を編集して同じ project で Content Directory を build し直すと、Scene に古い prefab が残ると分かりました。回避は、Scene に「焼き込む prefab のハッシュ」の印を持たせることでした。今回は、その印を source に一切残さない形と、prefab の file を読まない検知の鍵を測り、Scene 300 個の規模で build への上乗せを測った記録です。

範囲: repository の外の package を持たない空の project、Unity 6000.6.0f1、1 つの Unity process の batch で Content Directory の build 36 回（2026-11-14）。規模の fixture は合成で、Scene 300（1 つ約 1 MB、prefab の instance 420 個）、prefab 3,000（3 分の 1 は入れ子）、material 10、texture は無し。開いている Editor での build、Player の build、実データでは測っていません。

きっかけ

前の記事の回避は、印の置き場の GameObject を Scene に 1 つ置き、build の直前にその名前を prefab の中身のハッシュに書き換える形でした。これには 2 つの宿題が残っていました。置き場の object が source に残ること、そして印の値を作るために prefab の file を開いて中身を読むことです。また、入れ子の prefab と、複数の Scene が同じ prefab を置く場合は測っていませんでした。

そこで、次の 3 つを同時に満たす形を探しました。

  • cache が正しく効く: 編集した prefab を焼き込む Scene だけを作り直し、変更なしと前の版へ戻した build は前の出力を再利用する。
  • 検知が安い: prefab の file を開かずに編集を検知し、規模の project で、何も変えていない build への上乗せが印なしの build の 5% 以下。
  • source に残らない: build の後、Assets の下の全ての file が build の前と同じバイトで、印は出力にも残らない。

測った印の形

どちらの形も、build の直前に印の文字列を text として書き、build の後に元のバイトへ戻します。Scene を Unity の API で開いて保存することはしません。

形書く場所戻し方
MScene の .meta の userData の行（Scene 本体は書かない）元のバイトを書き戻す
F2Scene の file の末尾（最後の document の SceneRoots）に、Unity が知らない key の行を 1 つ足すfile を元の長さに切り詰める

M が成り立つのは、Scene の .meta も差分 build の再利用の鍵に入るからです。.meta の userData だけを変えた build で Scene は作り直され、元のバイトへ戻した build は前の出力を再利用しました。

印の値は、Scene の依存閉包のうち main asset が GameObject の物と ModelImporter が import した物を path の序数順に並べ、それぞれの検知の鍵の値を連ねてハッシュにしたものです。

検知の鍵: GetAssetDependencyHash を prefab ごとに引く

AssetDatabase.GetAssetDependencyHash（public）を prefab と model に対して引くと、次のように振る舞いました。

  • prefab と model の編集で値が変わり、元のバイトへ戻すと最初の値に戻った。更新時刻だけを変えても値は変わらなかった。
  • 入れ子の外側の prefab の値は、外側の file を変えなくても、内側の prefab の編集で変わった。
  • prefab が参照する texture や material を変えても、prefab の値は変わらなかった。

どれも file を開かずに得た値です。比べた他の鍵では、AssetDatabaseExperimental.LookupArtifact の ID は全ての時点で GetAssetDependencyHash と同じ値でした。internal の GetSourceAssetFileHash は file のバイトにだけ追従し、外側の prefab の値は内側の編集で変わりませんでした。build の鍵には GetAssetDependencyHash を使いました。

前の記事との食い違い

前の記事の「途中で分かったこと」には、GetAssetDependencyHash は prefab や texture を編集しても値が変わらず、依存の中身を表す値としては使えなかった、と書きました。あれは Scene に対して引いた値の話です。Scene の値は、Scene が置いた prefab を編集しても変わりません。一方、prefab そのものに対して引けば、上のとおり prefab の編集で変わり、入れ子の内側の編集にも追従します。だから、Scene が焼き込む prefab ごとに値を引いて連ねれば、検知の鍵になります。

cache の正しさと source（M と F2 で同じ）

  • 入れ子の内側の prefab、2 つの Scene が共有する prefab をそれぞれ編集した build は、編集した物を焼き込む Scene の serialized file だけを書き、他の Scene は書かなかった。
  • 変更なしの build と前の版へ戻した build は、Scene を 1 つも書かず、出力はその版の前回の出力と名前・sha256 で一致した。
  • model を編集した build も、その model を置いた Scene だけを書いた。ただし model の頂点は印なしでも出力に入る（Mesh は Scene に焼き込まれない）ので、これは印が model の編集を検知した証拠ではない。model の階層と Transform の編集は測っていない。
  • 全ての build の後、Assets の下の全ての file が build の前と同じバイトだった。印の文字列は出力に無く、印を書いた最後の build の出力は、同じ source を印なしで build した出力と Scene の file を含めて一致した。印による Error・Warning は無い。
  • 規模の fixture でも、source を変えない印ありの build は Scene を書かず、同じ出力を出した。

書いた数は、Unity が Library/BuildHistory に残す BuildContentTEP.json の BuildPipeline::WriteSerializedFile の event で数えました。

1 回目の失敗: Scene ごとに依存を列挙すると上乗せが 24〜32%

最初の batch では、印の値を作るために Scene ごとに GetDependencies(scene, true) で依存を列挙しました。cache の正しさと source の条件は両方の形で満たしましたが、何も変えていない build への上乗せが、印なしの build の約 24〜32% になりました。上乗せの約 8 割は印の値の計算で、300 Scene で約 3.0 秒かかり、その大半が Scene ごとの依存の列挙でした。

直し方は、依存の列挙を印の側でやめることです。製品の build 経路は、build の入力の snapshot を作る時に依存閉包を既に持っています。印の計算はその閉包を受け取り、自分では GetDependencies を呼ばない形に分けました。2 回目の batch では、閉包を作る所要を上乗せに入れずに別に記録しました。

この値の前提: 上の上乗せは、印の計算と書き込みを製品の snapshot の後・adapter の Refresh の前に置き、その snapshot の閉包をそのまま使う場合の値です。閉包を Refresh の後に作り直す形では、閉包を作る所要（製品の snapshot の所要ではなく、GetDependencies と除外だけの所要。この batch で 2,954〜3,480 ms、割る値の 18.7〜22.1%）を足して読み直します。足すと両形とも 5% を大きく超えます。

内訳から読めること

  • 印の計算は約 110 ms（約 0.7%）で、上乗せの約 8 割は書き込み・戻し・2 回の Refresh だった。
  • M は build の差を除くと 4.75〜4.80% でほぼ一定で、5% を超えた 2 回は build の差（53〜65 ms）の分だった。5% までの余裕は 31〜40 ms しかない。
  • F2 は、戻し（Scene 300 個の切り詰め）と戻し後の Refresh が M より重い。
  • 印なしの変更なしの build は約 15.7〜22.3 秒と揺れた（各 block の最初の回が約 6 秒遅い）。M の 5% の上下は、この揺れと 1 回ずつの build の差で分かれる。
  • 測っていない手順: 印の Refresh を製品の Refresh とまとめる、Scene の間で鍵の結果を使い回す。上乗せの大半はこの側にある。

OSM での扱い

  • 製品の build 経路への実装は次のスライスにする。印の形は M、検知の鍵は GetAssetDependencyHash から始め、F2 は不合格の代替として残す。
  • 次のスライスでは、まず上の前提（印の計算と書き込みを製品の snapshot の後・Refresh の前に置き、閉包をそのまま使う）が製品の形で成り立つかを確かめる。開いている Editor での build もそこで確かめ、結論が覆りうる。

測っていないこと

Player の build、別の PC・Library、実データ（SampleGame）、texture を持つ規模の fixture、prefab variant・override を持つ instance・unpack した prefab、model の階層と Transform の編集、開いている Editor での build（測ったのは batch だけ）、build が途中で落ちた時の Scene の戻し、開いている Scene と読み取り専用の file、印の他の形（印の object を Scene に差し込む形、YAML のコメント行）、file の更新時刻で全バイトの読みを省く検知、AssetPostprocessor で prefab の保存を拾う検知、BuildContentOptions.CleanBuildCache が CleanBuildCache() と同じ効果か、cache を消した build の所要。
