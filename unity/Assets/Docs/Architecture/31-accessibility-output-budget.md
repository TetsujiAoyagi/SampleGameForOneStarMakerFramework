## 1. 一文

全盲プレイの成否を決めるのは「オブジェクトに名前があるか」ではない。
**この瞬間、希少な出力に載せる価値のある少数は何か** である。

ラベルは前提条件（指差せる）であって難所ではない。難所は配送と調停である。

## 2. 本当に考えるべき問い

Web のアクセシビリティラベルは、静的で離散な文書を、文書順に読むための装置だった。[§30 §3](30-accessibility-identity.md#3-web-由来との差) が崩れる前提を書いた。

分解すると、満たすべき答えは 4 段ある。

| 段階 | 問い | 答えの置き場 | §30 だけで足りるか |
|---|---|---|---|
| 把握 | 何が在り、どの分類で、どこか | 記述子 + 位置供給元 | 番地としては足りる |
| 維持 | 前回から何が変わったか | 変更フィード（push） | **足りない。** ただし**新発明ではない** — `aria-live` のライブリージョンが Web での同じ機構である |
| 判断 | 今何ができるか | Focusable + Actionable | 候補としては足りる |
| 速度 | プレイのレートに間に合うか | **チャネル振り分け**が先、予算と調停が後 | **足りない。** ただし旧版が想定したほど調停は大きくない（下記） |

**旧版からの最大の変更:** キュー競合の大半は、**1 本のチャネルに全部載せたことの副作用**だった（[§30 §6.2](30-accessibility-identity.md#62-チャネルの二分--即時か説明的か)）。即時チャネル（触覚・非音声音・視覚の即時強調）と説明的チャネル（読み上げ・字幕・点検 UI）は帯域も予算の単位も違い、**同じキューは奪わない**。振り分けてから残る競合（同一チャネル内、および注意資源の同時提示）だけが本章の調停対象である。

1. **予算の単位は 1 つではない。** 説明的チャネルは「毎秒の語数」、即時チャネルは「**プレイヤーが区別を学習できる信号の種類数**」。同じ式で設計できない（数値の確定は §10）
2. 全部を読まない。落とすことが正常動作である
3. 差分を消費者が自前計算しない。レジストリ側が変更を出す
4. 「今の少数」を選ぶ方針は Game。機構（振り分け、キュー、割り込み、クールダウン、**集約**）は FW
5. 接近や残量のような連続量は、名前ではなく即時チャネルのパラメトリック符号化（ピッチ・強度・間隔）が運ぶ
6. **個別列挙をやめる（集約）のが、帯域の節約としては調停より効く可能性がある**（[§30 W-O-1](30-accessibility-identity.md#64-この表から出た未解決)）

## 3. 用語

| 用語 | 定義 |
|---|---|
| **即時チャネル** | 触覚 / 非音声音 / 視覚の即時強調。低レイテンシ。予算の単位は**区別できる信号の種類数** |
| **説明的チャネル** | 読み上げ / 字幕 / 点検 UI。学習不要。予算の単位は**毎秒の語数** |
| 振り分け | どちらのチャネルへ出すかの決定。**調停より先に来る** |
| 優先度クラス | **割り込み / キュー / 落とす**（`aria-live` の assertive / polite / off に対応） |
| 予算 | 単位時間あたりの発話量、同時鳴動、同一対象の再告知間隔、信号語彙の総数 |
| 変更フィード | Register / Unregister / SetFlags から出る差分。ライブリージョンのゲーム世界版 |
| 集約 | 複数の登録物を 1 つの告知に畳む機構（「敵が 3 体」）。**何を畳むかは Game、畳む機構は FW** |
| 顕著性 | 多数の登録物から「今載せる少数」を選ぶ規則。Game の方針 |
| 調停 | 振り分けと集約の後に残った競合を、予算内に収める FW の機構 |

## 4. 設計判断

### 4.1 決定

| # | 決定 | 根拠 |
|---|---|---|
| D-1 | **希少資源はラベルではなく出力チャネルと注意** | 名前を増やしても帯域は増えない |
| D-2 | **FW = 機構、Game = 方針** | 顕著性はゲーム固有性が最も高い。[§30 D-2](30-accessibility-identity.md) の「FW が分類を持つ」は識別層の話。配送の本丸では分担が逆 |
| D-3 | **変更フィードを第一級にする。ただし新発明として設計しない** | 維持の段階。Web は `aria-live` で同じ問題を解いており、語彙も振る舞いも借りられる |
| D-4 | **振り分けが先、調停が後。** `Urgent`（§30）は即時チャネルの**候補資格**であり、通知の行き先そのものではない | [§30 D-17](30-accessibility-identity.md)。振り分けは変更フィードのイベントごとに行う。残る競合だけが調停対象 |
| D-5 | **全部を読まない** | 落とすが正常 |
| D-6 | **連続量は記述子に載せない** | [§30 D-16](30-accessibility-identity.md)。即時チャネルのパラメトリック符号化で運ぶ |
| D-7 | **予算値は机上で発明しない** | サンプルの短時間プレイを書き下してから決める（§10）。**この決定は本章自身にも適用される** — 「信号の種類数の上限」も文献に確定値が無く、実測で決める |
| D-8 | **消費者ごとにキューを持たない** | 読み上げと字幕が別判断すると D-5 型の破壊 |
| D-9 | **優先度クラスは 3 つ（割り込み / キュー / 落とす）から始める** | `aria-live` は assertive / polite / off の 2 段 + off で 15 年以上運用されている。**旧版は 4 クラスを発明していたが、標準より多くする根拠が無い**。足りないと分かってから増やす |
| D-10 | **集約を機構として持つ** | 20 個の登録物を 20 回告知しないことが、予算調停より先に効く。畳む対象の選定は Game |

### 4.2 却下

| 却下 | 理由 |
|---|---|
| Urgent を優先度として扱う | D-4。優先度ではない |
| Urgent をオブジェクトの行き先そのものにする | D-4。行き先はイベントごと |
| **標準より細かい優先度クラスを最初から立てる** | D-9 |
| 即時チャネルと説明的チャネルを同じ予算式で設計する | 単位が違う（§3） |
| 消費者ごとキュー | D-8 |
| 全読み上げ | D-5 |
| 顕著性方針を FW が持つ | D-2。ゲームが変わると壊れる |
| 記述子にスカラ（距離変化率、残量）を足す | Identity がテレメトリバスになる。ホットパス契約が壊れる |
| Web の文書順をワールドに移植する | 距離・方位・緊急度が順序の正本 |

## 5. チャネル

特性のオーダー。数値予算は §10 の書き下し後に埋める。

| チャネル | 分類 | 運べるもの | 帯域の性質 | 今 |
|---|---|---|---|---|
| 視覚の即時強調（輪郭・コントラスト） | 即時 | 分類、位置、遮蔽 | 並列。**ロービジョンには最も効く** | [§24](24-rendering-system.md) Policy。**構想段階。** [§30 S-1](30-accessibility-identity.md#15-実装スライス) の消費者にはしない |
| 非音声音（定位、ピッチ、リズム、同時鳴動） | 即時 | 連続量。接近、方向、残量低下 | 並列に近い。言語を消費しない | やらない。SoundService は Phase 2 |
| 触覚 | 即時 | 衝撃、境界、方向 | 端末依存 | やらない |
| 音声（TTS / 発話） | 説明的 | 離散の事実。名詞、方位、動作句 | 極めて狭い。逐次。割り込みで前の文が死ぬ | やらない |
| 字幕 / 点検 UI の一覧 | 説明的 | 同上。**目で読める人には音声より速い** | 逐次だが読み飛ばせる | やらない |

### 5.1 即時チャネルの語彙は学習コストで選ぶ

即時チャネルは「覚える必要がある」が、その度合いは一様ではない。HCI の実測では、習得に要する訓練回数は

**auditory icon（実世界の音。扉の軋み = 扉）< spearcon（極端に時間圧縮した音声）< earcon（抽象的な音型）**

の順で、spearcon と speech は平均 1.14 回で正答率 100% に達する一方、earcon は最も多くを要する。

したがって **「速い」と「学習不要」は両立しうる**（spearcon）。即時チャネルの語彙は、抽象的な音型を発明する前に auditory icon と spearcon を検討する。

なお**信号の種類数の上限には、文献に確定値が無い**（実務側の指針は「少数に絞り、区別しやすくせよ」に留まる）。D-7 により、値は §10 の実測で決める。

## 6. 優先度と予算

**振り分けが先である**（D-4）。即時チャネルへ出るものは、説明的チャネルのキューを一切消費しない。以下は**説明的チャネル内**の話である。

優先度クラス（FW）。`aria-live` に倣い 3 つから始める（D-9）:

| クラス | 対応 | 意味 | 例 |
|---|---|---|---|
| 割り込み | `assertive` | 進行中の発話を止め、キューを捨ててよい | 落下、即死級 Hazard |
| キュー | `polite` | 止めない。手が空いたら言う | Region 入場、目標達成、近くの Actionable |
| 落とす | `off` | 言わない | 遠い Decorative、クールダウン中の再告知 |

旧版はここに「キュー先頭」を加えた 4 クラスを置いていた。**標準より細かくする根拠が無いので落とした。** 必要だと分かってから足す。

予算の項目（値は未定。§10）:

| チャネル | 予算項目 |
|---|---|
| 説明的 | 単位時間あたりの発話語数上限 / 同一 StableId の再告知クールダウン / キュー長 |
| 即時 | 同時鳴動数 / **信号語彙の総数**（区別を学習できる上限） |

機構は FW。どの Kind がどのクラスかは Game の方針テーブル。

## 7. 変更フィード

「維持」を埋める。**Web の `aria-live` と同じ問題に対する、同じ形の解である。** 新しい概念として設計しない。

材料は §30 レジストリの Register / Unregister / SetFlags。本章は購読口を持つ。

```
Added(handle)
Removed(stableId)
FlagsChanged(handle, old, new)
```

消費者が毎フレーム全件を取って diff しない。全件の切断面が要るときだけ pull で問い合わせる。

通知はコールド（変更は人間スケール）。ホットパスで文字列を配らない。Handle を載せる。

## 8. 顕著性と集約

400 個から「今の少数」を選ぶ規則。ゲーム固有性の本丸。**方針は Game が持つ。**

FW が用意する機構:

- 候補列（Query + 変更フィード）
- **チャネル振り分け**（D-4）
- **集約** — N 件を 1 件に畳む（D-10）。「敵が 3 体」「棚に 5 個」
- 予算と優先度クラス
- クールダウン

Game が決める方針（例。サンプル固有の表は Game.Common に置く）:

- 今いる Region の入場はキュー
- 視点前方の Hazard は割り込み候補
- 巡回中の Actionable は通常キュー
- Decorative は落とす
- **同じ Kind が近接して N 件以上あれば畳む**（畳む条件は Game、畳む処理は FW）

FW が「Threat は常に割り込み」と決めない。

> **集約は未実装かつ未設計である**（[§30 W-O-1](30-accessibility-identity.md#64-この表から出た未解決)）。粒度（距離で畳むか、Kind で畳むか、階層で畳むか）が決まっていない。**帯域への効きは調停より大きい可能性があるので、実装順では調停より先に検討する。**

## 9. 連続量

「接近中」「残量低下」「溜め動作中」は Flags では表せない。`SetFlags` はイベント型（離散遷移）である。

**スコープ外（決定）:** 記述子にスカラ経路を足さない。運ぶのは非音声音、または Game の音響設計（既存の Cue を定位させる）。識別層は「それは Hazard である」まで。どれだけ近いかは位置供給元を音側が読む。

後でスカラが Identity に必要だと分かったら、本章の撤退ラインではなく **新契約** として足す。§30 を拡張して済ませない。

## 10. 予算の決め方

数値を机上で発明しない（D-7）。**これは本章自身にも適用される** — 「信号語彙の上限」を文献から引けなかったので、同じ手順で決める。

対象は今あるサンプルの InGame: セルストリーミングの世界を、飛行で数十秒動く。ジャンル固有の「季節トンネル」や STG の弾幕は使わない（まだそのゲームではない）。

手順:

1. 視点が Cell をまたぎ、作者物（Marker / Prop）と HUD がある状態を 30 秒分、全盲プレイヤーが**秒単位で何を聞くか / 何を音で感じるか**を書き下す
2. **書き下しを 2 列に分ける** — 即時チャネル（音・触覚・強調）と説明的チャネル（発話・字幕）。これが振り分け方針の初稿になる
3. 説明的列から**発話語数上限とクールダウン**を、即時列から**同時鳴動数と信号語彙の総数**を決める
4. **同じ Kind が近接して何件出たかを数える。** 集約（D-10）で何割減るかの実測値になる
5. Label が何回登場したかを数える。予測は「UI と選択時に偏る」
6. 結果を §13 に記録する。必要なら [§30 §15](30-accessibility-identity.md#15-実装スライス) の S-1 / S-2 の順を差し替える

この書き下し自体も **今やらない**（契約として手順だけ固定する）。実装スライスより前、音を足すより前に半日でやる作業、と位置づける。

## 12. 撤退ライン

1. 全読み上げに戻さない（D-5）
2. **チャネル振り分けを捨てて 1 本のキューに戻さない**（D-4）。調停の複雑さはそこから来ていた
3. 顕著性を FW の Kind 表に固定しない（D-2）
4. 連続量を §30 記述子に逃がさない（D-6）
5. 消費者ごとキューに分解しない（D-8）
6. 予算値を実測せずに確定しない（D-7）

機構（振り分け、集約、1 本の調停、変更フィード、予算項目）は撤退しても残す。
