## 1. 一文

全盲プレイの成否を決めるのは「オブジェクトに名前があるか」ではない。
**この瞬間、希少な出力に載せる価値のある少数は何か** である。

ラベルは前提条件（指差せる）であって難所ではない。難所は配送と調停である。

---

## 2. 本当に考えるべき問い

Web のアクセシビリティラベルは、静的で離散な文書を、文書順に読むための装置だった。[§30 §3](30-accessibility-identity.md#3-web-由来との差) が崩れる前提を書いた。

分解すると、満たすべき答えは 4 段ある。

| 段階 | 問い | 答えの置き場 | §30 だけで足りるか |
|---|---|---|---|
| 把握 | 何が在り、何と呼ぶか、どこか | 記述子 + 位置供給元 + pull Snapshot | 番地としては足りる |
| 維持 | 前回から何が変わったか | 変更フィード（push） | **足りない。** Snapshot はポーリング |
| 判断 | 今何ができるか | Focusable + Actionable + Hint | 候補としては足りる |
| 速度 | プレイのレートに間に合うか | 予算・優先度・顕著性 | **足りない。** Urgent 1 ビットでは調停にならない |

タグ / ラベル / ヒントが扱わない、と §30 が言っていた領域が、全盲向けには本丸である。扱わないことを責めるのではなく、**別契約として立てる**。

満たすべき答え:

1. 音声は毎秒数語しか運べない、を設計の入力にする（数値の確定は §10）
2. 全部を読まない。落とすことが正常動作である
3. 差分を消費者が自前計算しない。レジストリ側が変更を出す
4. 「今の少数」を選ぶ方針は Game。機構（キュー、割り込み、クールダウン）は FW
5. 接近や残量のような連続量は、名前ではなく非音声音（または Game の音響）が運ぶ

## 3. 用語

| 用語 | 定義 |
|---|---|
| チャネル | 音声 / 非音声音 / 触覚 / 視覚補助。帯域が違う |
| 優先度クラス | 割り込み / キュー先頭 / 通常キュー / 落とす |
| 予算 | 単位時間あたりの発話量、同時鳴動、同一対象の再告知間隔 |
| 変更フィード | Register / Unregister / SetFlags から出る差分。pull Snapshot の対 |
| 顕著性 | 多数の登録物から「今載せる少数」を選ぶ規則。Game の方針 |
| 調停 | 競合する告知を、予算内に畳む FW の機構 |

## 4. 設計判断

### 4.1 決定

| # | 決定 | 根拠 |
|---|---|---|
| D-1 | **希少資源はラベルではなく出力チャネルと注意** | 名前を増やしても帯域は増えない |
| D-2 | **FW = 機構、Game = 方針** | 顕著性はゲーム固有性が最も高い。[§30 D-2](30-accessibility-identity.md) の「FW が分類を持つ」は識別層の話。配送の本丸では分担が逆 |
| D-3 | **変更フィードを第一級にする** | 維持の段階。Snapshot の自前差分は系統ごとにバラける（識別層の D-5 と同型） |
| D-4 | **Urgent は資格、優先度クラスは本章** | §30 の 1 ビットは「割り込んでよいか」。キュー操作はここ |
| D-5 | **Announcable を全部読まない** | 落とすが正常 |
| D-6 | **連続量は記述子に載せない** | [§30 D-16](30-accessibility-identity.md)。非音声音か Game 音響 |
| D-7 | **予算値は机上で発明しない** | サンプルの短時間プレイを書き下してから決める（§10） |
| D-8 | **消費者ごとにキューを持たない** | 読み上げと字幕が別判断すると D-5 型の破壊 |

### 4.2 却下

| 却下 | 理由 |
|---|---|
| Urgent 1 ビットのまま配送を済ませる | 資格と調停が混ざる |
| 消費者ごとキュー | D-8 |
| Announcable 全読み上げ | D-5 |
| 顕著性方針を FW が持つ | D-2。ゲームが変わると壊れる |
| 記述子にスカラ（距離変化率、残量）を足す | Identity がテレメトリバスになる。ホットパス契約が壊れる |
| Web の文書順をワールドに移植する | 距離・方位・緊急度が順序の正本 |

## 5. チャネル

特性のオーダー。数値予算は §10 の書き下し後に埋める。

| チャネル | 運べるもの | 帯域の性質 | 今 |
|---|---|---|---|
| 音声（TTS / 発話） | 離散の事実。名詞、方位、Hint | 極めて狭い。逐次。割り込みで前の文が死ぬ | やらない |
| 非音声音（定位、ピッチ、リズム、同時鳴動） | 連続量。接近、方向、残量低下 | 並列に近い。言語を消費しない | やらない。SoundService は Phase 2 |
| 触覚 | 衝撃、境界 | 端末依存 | やらない |
| 視覚補助 | ハイコントラスト、ブリップ | 全盲には届かない。ロービジョン・片腕の補助 | やらない |

予測（§10 で反証する）: 有用な出力の多くは非音声かつ連続で、Label の登場は UI と「今これを選んだ」ときに偏る。それが確認されたら、実装順はラベル経路より位置と音の経路が先、になりうる。そのときは [§30 §14](30-accessibility-identity.md#14-実装スライス) を差し替える。

## 6. 優先度と予算

優先度クラス（FW）:

| クラス | 意味 | 例 |
|---|---|---|
| 割り込み | 進行中の発話を止めてよい | 落下、即死級 Hazard。§30 `Urgent` かつ Game 方針が許可 |
| キュー先頭 | 止めないが次に言う | Region 入場、目標達成 |
| 通常キュー | 予算が空けば言う | 近くの Interactable |
| 落とす | 言わない | 遠い Decorative、クールダウン中の再告知 |

予算の項目（値は未定。§10）:

- 単位時間あたりの発話語数上限
- 同時鳴動数（非音声音）
- 同一 StableId の再告知クールダウン

機構は FW。どの Kind がどのクラスかは Game の方針テーブル。

---

## 7. 変更フィード

「維持」を埋める。

材料は §30 レジストリの Register / Unregister / SetFlags。本章は購読口を持つ。

```
Added(handle)
Removed(stableId)
FlagsChanged(handle, old, new)
```

消費者が Snapshot を毎フレーム取って diff しない。Snapshot は「今の空間切断面」が欲しいときだけの pull。

通知はコールド（変更は人間スケール）。ホットパスで文字列を配らない。Handle の Slot を載せる。

---

## 8. 顕著性

400 個から「今の少数」を選ぶ規則。ゲーム固有性の本丸。**Game が持つ。**

FW が用意するもの:

- 候補列（Query + 変更フィード）
- 予算と優先度クラス
- クールダウン

Game が決めるもの（例。サンプル固有の表は Game.Common に置く）:

- 今いる Region の入場はキュー先頭
- 視点前方の Hazard は割り込み候補
- 巡回中の Actionable は通常キュー
- Decorative は落とす

FW が「Threat は常に割り込み」と決めない。

---

## 9. 連続量

「接近中」「残量低下」「溜め動作中」は Flags では表せない。`SetFlags` はイベント型（離散遷移）である。

**スコープ外（決定）:** 記述子にスカラ経路を足さない。運ぶのは非音声音、または Game の音響設計（既存の Cue を定位させる）。識別層は「それは Hazard である」まで。どれだけ近いかは位置供給元を音側が読む。

後でスカラが Identity に必要だと分かったら、本章の撤退ラインではなく **新契約** として足す。§30 を拡張して済ませない。

---

## 10. 予算の決め方

数値を机上で発明しない。

対象は今あるサンプルの InGame: セルストリーミングの世界を、飛行で数十秒動く。ジャンル固有の「季節トンネル」や STG の弾幕は使わない（まだそのゲームではない）。

手順:

1. 視点が Cell をまたぎ、作者物（Marker / Prop）と HUD がある状態を 30 秒分、全盲プレイヤーが**秒単位で何を聞くか / 何を音で感じるか**を書き下す
2. その書き下しから、発話語数上限と同時鳴動数を決める
3. Label が何回登場したかを数える。予測は「UI と選択時に偏る」
4. 結果を本章のオープン論点に記録する。必要なら §30 S-1 / S-2 の順を差し替える

この書き下し自体も **今やらない**（契約として手順だけ固定する）。実装スライスより前、音を足すより前に半日でやる作業、と位置づける。

## 11. 今やらない

| 項目 | 理由 |
|---|---|
| TTS / SoundService / キュー実装 | Phase 2 未着手 |
| 変更フィードの C# | §30 S-1 の Registry が先 |
| 顕著性テーブルの中身 | サンプルに脅威もインタラクトもほぼ無い |
| 予算の確定値 | §10 の書き下しが先 |
| 触覚 | 端末依存。要求が無い |
| 字幕パイプライン | 同じ調停を読む別シンク。機構の後 |
| AI アシスタントの発話 | 同じ予算を食う消費者。機構の後 |
| 記述子へのスカラ | D-6 |

---

## 12. 撤退ライン

1. Announcable 全読み上げに戻さない
2. 顕著性を FW の Kind 表に固定しない
3. 連続量を §30 記述子に逃がさない
4. 消費者ごとキューに分解しない

機構（1 本の調停、変更フィード、予算項目）は撤退しても残す。

## 13. オープン論点

| # | 論点 | 現時点の見立て |
|---|---|---|
| O-1 | 30 秒書き下しの結果 | 未実施。発話語数と Label 登場回数をここに記す |
| O-2 | §30 実装順の差し替え | 非音声が主なら距離前段と Sound をラベル UI より前にする |
| O-3 | 方位語彙 | 時計回り。書き下しで違和感が出たら見直す |
| O-4 | 字幕を音声と同一キューにするか | 同一調停、別レンダラが有力 |
