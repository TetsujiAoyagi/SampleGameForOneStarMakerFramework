## 6.1 暗黙知の言語化

| # | 暗黙知 | 必要な理由 |
|---|---|---|
| IK-6 | 1シーン = 0 or 1 UIView。UIView を分けたいなら子シーンを分ける | ライフサイクル管理の単純化。1:N は管理コストが爆発する |
| IK-7 | UIView はなるべく使う単位でまとめる。巨大な MainMenu は禁止 | ロード時間・メモリ・保守性の全てが悪化する |
| IK-8 | ただしシーン分割しすぎるとロード回数増加。ロード時間は極小を維持する | PreLoad + 親子ツリー同時ロードで緩和する |
| IK-10 | **UI Toolkit 直行済み**。uGUI 経路は Debug 用レガシー（`DebugProfilerView` のみ）として暫定維持。ViewIn/ViewOut/UILayer の抽象は変わらない | 現行画面は UI Toolkit。uGUI の SetParent 方式はレガシー経路に限定 |
| IK-11 | **非UIレンダラ（パーティクル / Live2D / Spine）を UI 描画順の任意深度に挟む手段は未確立**。UITK にノード単位のマテリアル指定が無く、単一パネル構造ではソートスロットも1つしかない | 「2Dキャラを最前面、エフェクトはその後ろ」のような画面構成が現状では表現できない。検討は [29-ui-effect-compositing.md](29-ui-effect-compositing.md) |

> UI 演出パイプライン（MVVM + Behavior）の概念モデルは [§6.17](#617-behavior-パイプライン--状態と時間の分離)、実装契約は [§6.16](#616-バインディング契約と状態の所有権)。

## 6.2 施行ルール

| # | ルール | 施行方法 | 強制力 |
|---|---|---|---|
| E-1 | 1シーン = 0 or 1 UIView | SceneBase.Initialize が UIView を1つだけ検索 | 構造的強制 |
| E-2 | **[uGUI レガシー限定]** シーン上の UIView は Canvas の**直下**に配置する。移動対象は UIView GO のみ（UI Toolkit ビューは Canvas 不要） | SceneBase.Initialize が Canvas 直下の UIView を検索し UIView GO を渡す | 構造的強制 + 規約 |
| E-3 | **[uGUI レガシー限定]** 動的要素（アニメーション・スクロール）は sub-canvas で隔離 | コードレビュー + Editor バリデーション（将来） | 規約 |
| E-4 | LitMotion: GameObject にバインドする場合は `.AddTo(gameObject)` 必須。VisualElement 対象の場合は BehaviorRunner の CancellationToken で寿命を保証する | コードレビュー | 規約 |
| E-5 | ViewOut は非キャンセル（CancellationToken なし） | メソッドシグネチャで強制 | 構造的強制 |
| E-6 | 巨大 UIView（MainMenu 等）を作らない | コードレビュー。目安: 1 UIView の要素数 < 50 | 規約 |
| E-7 | ViewModel は `VisualElement` を参照しない。Visual State（時間補間中の値）を保持しない | コードレビュー（§6.16 の分類表で判定） | 規約 |
| E-8 | 要素取得（`Q()`）とバインドは `OnRootCreated` に閉じ、購読は `IDisposable` で寿命管理する | コードレビュー | 規約 |

## 6.3 トレードオフ判定

| 決定 | 採用 | 却下理由 |
|---|---|---|
| ソート権威 | **SiblingIndex（階層順）** | sortingOrder 方式は UIView ごとに sub-canvas(overrideSorting) が必要で Canvas.BuildBatch コスト増。SiblingIndex なら単一 Canvas でバッチ結合可能 |
| 1シーン:UIView | **1:1** | 1:N は管理コスト・ライフサイクル整合性の複雑さが大きすぎる |
| UILayer | **6レイヤー** | 3レイヤーでは要件の Background/Normal/Modal/Dialog/Loading/Debug を表現できない |
| 元 Canvas | **UIView GO のみ移動**（Canvas はシーンに残す） | 「最初から持たない」は Prefab プレビューで見えない。「Destroy」はフレーム遅延リスク。移動のみが最もシンプル |
| Canvas 効率化 | **sub-canvas で動的要素隔離（規約）** | UICommon をレイヤー別に Canvas 分割する案は管理が複雑すぎる |
| 入力ブロック | **Modal/Dialog 表示時に透明 Blocker 自動生成** | UICommon 全体の GraphicRaycaster on/off では粒度が粗すぎる |
| UI 実装 | **UI Toolkit 直行**（uGUI は Debug レガシーのみ） | Phase 4 段階移行案は不採用。抽象インターフェース（ViewIn/ViewOut/UILayer）は維持 |

> **注:** 本決定は「非UIレンダラ（パーティクル等）を UI 描画順の任意深度に挟む」要求を検討対象に入れていない（IK-11）。当該要求の扱いは [29-ui-effect-compositing.md](29-ui-effect-compositing.md) で検討中であり、結論次第では本行の改訂があり得る。

## 6.4 設計原則

```
1シーン = 0 or 1 UIView（明示的なルール）
全 UIView は UICommon（DontDestroyOnLoad な共通ルート = PanelRenderer + レガシー Canvas）の子として管理される
描画順の権威:
  - UI Toolkit（現行）: レイヤーコンテナ構造 + 同レイヤー内 Stack（後入れが末尾 = 前面）
  - uGUI（レガシー）: SiblingIndex（階層順。6レイヤー × Stack、UICommon が SetSiblingIndex で管理）
```

### UIView の階層構造

```
[シーン上]                    [AddUIView 後]
Scene (Unity Scene)           UICommon (Canvas, DontDestroyOnLoad)
└── Canvas                    ├── ... 既存の UIView 群
    └── UIView GO             └── UIView GO        ← SetParent で移動
        └── children              └── children

※ シーンの Canvas はシーンに残り、Unload で自然消滅
※ UIView GO 自体は Canvas を持たない（UICommon Canvas のバッチに含まれる）
```

## 6.5 UILayer（6レイヤー）

```csharp
public enum UILayer
{
    Background = 0,  // 背景 UI（スカイボックス、背景エフェクト等）
    Normal     = 1,  // 通常 UI（HUD、メニュー等）
    Modal      = 2,  // モーダル UI（背面入力ブロック付き。例: 設定画面、インベントリ全画面）
    Dialog     = 3,  // ダイアログ UI（確認・選択ポップアップ。例: 「本当に削除しますか？」）
    Loading    = 4,  // ローディング UI（全入力ブロック）
    Debug      = 5,  // デバッグ UI（FPS、メモリ、デバッグメニュー。Blocker なし）
}
```

> **Modal vs Dialog の使い分け:** Modal は「画面全体を占有する UI」（設定、インベントリ等）。Dialog は「小さなポップアップ」（確認ダイアログ、エラー表示等）。どちらも背面 Blocker が自動生成されるが、Dialog は Modal より前面に描画されるため、Modal 画面上に Dialog を重ねて表示できる。

### 描画順（SiblingIndex）

> **本小節は uGUI レガシー経路の規定である。** UI Toolkit 経路では、描画順はレイヤーコンテナ構造 + 同レイヤー内は後入れ末尾（= 前面）で決まる（§6.7 参照）。

UICommon の子として配置された UIView は、**SiblingIndex が小さいほど奥、大きいほど前面**に描画される。
UICommon は LinkedList でレイヤー順を管理し、`SetSiblingIndex` で以下の順序を維持する：

```
SiblingIndex 小 → 大（奥 → 前面）:
  Background の UIView 群
  → Normal の UIView 群
  → Modal の Blocker + UIView 群
  → Dialog の Blocker + UIView 群
  → Loading の Blocker + UIView 群
  → Debug の UIView 群（Blocker なし）
```

同レイヤー内では Stack 方式: 後から追加された UIView ほど SiblingIndex が大きい（= 前面）。

## 6.6 UIView のライフサイクル

```csharp
public abstract class UIView : MonoBehaviour
{
    public enum UILayer
    {
        Background = 0,
        Normal     = 1,
        Modal      = 2,
        Dialog     = 3,
        Loading    = 4,
        Debug      = 5,
    }

    /// <summary>入場アニメーション。</summary>
    public virtual UniTask ViewIn(CancellationToken ct) => UniTask.CompletedTask;

    /// <summary>退場アニメーション。キャンセル不可。</summary>
    public virtual UniTask ViewOut() => UniTask.CompletedTask;

    /// <summary>この UIView のレイヤーを返す。</summary>
    public virtual UILayer GetUILayer() => UILayer.Normal;
}
```

## 6.7 UICommon の AddUIView フロー

UICommon は `UIToolkitView` と uGUI `UIView` を分岐で管理する。UILayer 6 層・Stack 方式・Blocker 自動生成の契約は両経路で共通。

### UI Toolkit 経路（現行）

`UIToolkitView` の場合、パネルの root（`PanelRenderer` の `UIReloadCallback` で受領）直下に構築済みの UILayer コンテナ（`Layer-Background` 等）へ `Root` を挿入する。`Root` は Framework 所有のフルサイズ Host であり、`VisualTreeAsset.CloneTree(Root)` により UXML の最上位要素をその直下へ展開する。Background の Stretch、Dialog の中央寄せ、HUD の端固定などの画面固有レイアウトは **UXML/USS の最上位要素**が定義する。`CloneTree()` の戻り値である `TemplateContainer` を直接 Root にしてはならない（サイズ未決定の Wrapper が `height: 100%` を 0 に潰し得る）。

> **注**: `UIDocument` は Unity 6.5 で obsolete となり、Inspector から新規追加できない。UICommon は後継の `PanelRenderer` を使用する。`PanelRenderer` は root を直接公開しないため、`RegisterUIReloadCallback`（version 付き）で root を受け取り、そこでレイヤーコンテナを構築する。

```
AddUIView(ownerId, view: UIToolkitView, ct)
  │
  ├─ [1] LinkedList にレイヤー順で挿入（同レイヤー内は末尾 = Stack 方式）
  │
  ├─ [2] 該当レイヤーコンテナへ view.Root を Add（後入れが末尾 = 前面）
  │
  ├─ [3] Modal/Dialog/Loading レイヤーなら Blocker を自動生成
  │       フルスクリーン透明 VisualElement（pickingMode = Position）
  │       Blocker を UIView の直前に Insert
  │
  └─ [4] await view.ViewIn(ct)
```

```
RemoveUIView(ownerId)  ※ UIToolkitView
  │
  ├─ [1] await view.ViewOut()
  ├─ [2] Blocker があれば RemoveFromHierarchy
  ├─ [3] LinkedList から除去
  └─ [4] view.Root.RemoveFromHierarchy()
```

レイヤーコンテナ自体は `pickingMode = Ignore`（入力透過）。Blocker のみ `pickingMode = Position` で背面入力を遮断する。

### uGUI 経路（レガシー）

```
AddUIView(ownerId, view, ct)
  │
  ├─ [1] view.transform.SetParent(uiCommon.transform, false)
  │
  ├─ [2] LinkedList にレイヤー順で挿入（同レイヤー内は末尾 = Stack 方式）
  │       FindInsertPosition: 「自分より大きいレイヤー」の直前に挿入
  │       → 同レイヤーの最後に入る = 後入れが後ろ = SiblingIndex が大きい = 前面
  │
  ├─ [3] Modal/Dialog/Loading レイヤーなら背面 Blocker を自動生成
  │       フルスクリーン透明 Image（raycastTarget = true）
  │       Blocker は UIView の直前の SiblingIndex に配置
  │
  ├─ [4] RefreshSiblingOrder()（LinkedList の順序を SetSiblingIndex に反映）
  │
  └─ [5] await view.ViewIn(ct)
```

### RemoveUIView フロー（uGUI 経路）

```
RemoveUIView(ownerId)
  │
  ├─ [1] await view.ViewOut()
  ├─ [2] Blocker があれば Destroy
  ├─ [3] LinkedList から除去
  ├─ [4] view.transform.SetParent(null, false)
  └─ [5] RefreshSiblingOrder()（残存 UIView の SiblingIndex を再設定）
```

## 6.8 技術選定

**UI Toolkit で開始する。** 新規画面は `UIToolkitView`（UXML + MVVM + Behavior Pipeline）で実装する。uGUI 経路は `DebugProfilerView` 等の Debug 用レガシーのみ暫定維持する。

### 実装経路の対比

| 変更点 | 現行（UI Toolkit） | レガシー（uGUI, DebugProfilerView のみ） |
|---|---|---|
| UIView の基底 | `UIToolkitView`（`VisualTreeAsset` + `Root`） | `MonoBehaviour` + RectTransform |
| UICommon への挿入 | レイヤーコンテナへ `Root.Add` / `Insert` | `SetParent` + `SetSiblingIndex` |
| 描画順 | レイヤーコンテナ構造 + 同レイヤー内 Stack | SiblingIndex（階層順） |
| アニメーション | Behavior Pipeline + LitMotion for UI Toolkit | LitMotion（ViewIn/ViewOut 直書き） |
| 入力ブロック | 透明 Blocker `VisualElement`（`pickingMode = Position`） | 透明 Blocker Image + GraphicRaycaster |

**変わらないもの:**
- `ViewIn` / `ViewOut` の async インターフェース
- UILayer によるソート（6レイヤー）
- UICommon による一元管理
- 1シーン = 0 or 1 UIView の原則

## 6.9 アニメーションの実装ルール

```csharp
// ✗ やってはいけない: Tween と Delay が独立して動く
public override async UniTask ViewIn(CancellationToken ct)
{
    var tweener = transform.DOLocalMoveX(0f, 1f);
    await UniTask.Delay(1000, cancellationToken: ct);
    // 問題: TimeScale でズレる。Delay キャンセルで tweener.Kill() が呼ばれない
}

// ✓ 旧プロジェクト（DOTween）の正しいパターン
public override async UniTask ViewIn(CancellationToken ct)
{
    await transform
        .DOLocalMoveX(0f, 1f)
        .SetLink(gameObject)
        .ToUniTask(cancellationToken: ct);
}

// ✓ 新プロジェクト（LitMotion）の標準パターン
public override async UniTask ViewIn(CancellationToken ct)
{
    await LMotion.Create(transform.localPosition.x, 0f, 1f)
        .BindToLocalPositionX(transform)
        .AddTo(gameObject)       // GameObject 破棄時に自動キャンセル
        .ToUniTask(ct);
}
```

**ルール:**
- LitMotion を使う場合は `.AddTo(gameObject)` を必ず付ける（リーク防止）。
- `.ToUniTask(ct)` で Tween 自体を await する。別途 Delay を使わない。

## 6.10 Unload 時に ViewOut を必ず呼ぶ

RemoveScene / CleanupCanceledScene 内で、§5.8 の3フェーズアンロードに従い ViewOut を実行する。
ViewOut は非キャンセル（CancellationToken なし）。

```csharp
// SceneDirector のアンロードフロー（概要）:
// Phase 1: 全子孫の ViewOut + PreUnload（全 Unity Scene が残存 → sibling 参照可能）
await _uiCommon.RemoveUIView(sceneIdentify);  // ViewOut() + Blocker Destroy
await sceneBase.ExecutePreUnLoad();            // PreUnload フック

// Phase 2: 全子孫の Unity Scene アンロード
await PerformUnitySceneUnload(sceneId, handle);

// Phase 3: 全子孫の AfterUnload + Dispose + 辞書除去
await sceneBase.ExecuteAfterUnLoad();
sceneBase.Dispose();
```

## 6.11 UICommon と SceneBase の依存方向

```
// ✗ 双方向依存（旧プロジェクト）
UICommon → SceneBase（Key として保持）
SceneBase → UICommon（AddUIView / RemoveUIView を呼ぶ）

// ✓ 一方向依存（本プロジェクト）
SceneDirector → UICommon（仲介者として AddUIView / RemoveUIView を呼ぶ）
SceneDirector → SceneBase（UIView を取得する）
UICommon は SceneBase を知らない（string ownerId で管理）
```

## 6.12 入力ブロック

Modal / Dialog / Loading レイヤーの UIView が表示されると、背面への入力を自動ブロックする。

```
SiblingIndex（小 → 大 = 奥 → 前面）:
  [0] Background  HUD                        ← Blocker で入力遮断
  [1] Normal      InventoryMenu              ← Blocker で入力遮断
  [2] Dialog      ─── Blocker ───            ← raycastTarget=true で背面を遮断
  [3] Dialog      ConfirmDialog              ← 入力可能（最前面）
```

- Blocker は AddUIView で**自動生成**、RemoveUIView で**自動削除**
- UILayer が Modal〜Loading のとき、UIView の直前に Blocker を挿入する（Debug レイヤーは Blocker なし）
- Blocker はフルスクリーン透明 Image（`raycastTarget = true`）
- 複数 Modal/Dialog が重なった場合、最前面の UIView のみ入力可能
- Blocker は複数生成されるが意図的。実効は最前面の Blocker のみ
- Debug レイヤーは背面の入力をブロックしない（ゲームプレイしながらデバッグ情報を確認可能）

## 6.13 Canvas 効率化ガイドライン

### UICommon Canvas（ルート）

- UICommon Canvas 自体は**静的**（レイアウト変更しない）
- UIView の描画順は SiblingIndex（階層順）で制御する（sub-canvas 自動付与なし）
- UIView は UICommon Canvas のバッチに含まれる

### UIView 内の sub-canvas（開発者が必要に応じて手動配置）

sub-canvas は描画順制御ではなく、**動的要素の batch 隔離**のために使用する。

| 用途 | 例 |
|---|---|
| スクロールリスト | アイテム一覧、ランキング |
| 頻繁に更新される要素 | HP バー、カウントダウン、スコア |
| アニメーション要素 | エフェクト、遷移アニメーション |

**ルール:**
- アニメーション・スクロール・頻繁に更新される要素は、sub-canvas で囲む（推奨）
- 静的な要素（背景、テキスト等）は sub-canvas 不要
- sub-canvas の `overrideSorting` は**使わない**（SiblingIndex による描画順を壊すため）
- UIView が sub-canvas を持たなくても正常動作する（UICommon Canvas のバッチに含まれる）

## 6.14 uGUI レガシー経路

`DebugProfilerView` 等、uGUI ベースの UIView が残存する間に適用する暗黙知。新規画面では参照しない。

| # | 暗黙知 | 必要な理由 |
|---|---|---|
| IK-1 | `SetParent(uiCommon, false)` 時にワールド座標は保持されない。UIView の RectTransform は stretch anchor 前提 | レイアウト崩れ防止 |
| IK-2 | シーン上の UIView 配置は `Canvas → UIView GO → children` の階層とする。`AddUIView` 時は **UIView GO のみ** を UICommon に移動する。元 Canvas はシーンに残り、シーン Unload で自然消滅する | Canvas 2重化を構造的に回避。Destroy 不要でフレーム遅延問題も発生しない |
| IK-3 | UIView の子に sub-canvas を持ってよい。その場合 sub-canvas に GraphicRaycaster も必要 | DrawCall は sub-canvas 単位でバッチが切れるが、動的要素の隔離のために許容する |
| IK-4 | **SiblingIndex（階層順）が描画順の権威**。UICommon が LinkedList でレイヤー順を管理し `SetSiblingIndex` で反映する | 単一 Canvas 配下では階層順 = 描画順。sortingOrder ベースより再計算コストが低い |
| IK-5 | 同一レイヤー内は Stack 方式（後入れが前面）。UICommon が SiblingIndex で後入れを後方（= 前面）に配置する | 明示的な順序指定なしで直感的な重なりを実現 |
| IK-9 | UICommon Canvas 1枚に全 UIView を集約すると Canvas.BuildBatch が全体リビルドされる | 動的要素を持つ UIView は sub-canvas で隔離する（開発者の責務） |

uGUI 経路の AddUIView / RemoveUIView フローは §6.7 を参照。Canvas 効率化ガイドライン（§6.13）も uGUI レガシー向けである。

## 6.15 将来の拡張（Phase 2 以降）

本設計は Phase 1 のシューティングゲームに必要十分な「薄いフレームワーク」を目指す。
以下の機能は Phase 2 以降で必要に応じて追加する。

### FE-1: 同時トランジション

現状 `ViewOut` → `ViewIn` は直列実行。「前画面がスライドアウトしながら次画面がスライドイン」のような並列トランジションが必要になった場合に拡張する。

**拡張方針:** SceneDirector の SwitchScene に `TransitionMode.Parallel` オプションを追加。ViewOut/ViewIn のシグネチャは変えず、SceneDirector が `UniTask.WhenAll` で並列実行する。

### FE-2: Dialog の動的生成とプーリング

現状 UIView はシーンに配置される前提。繰り返し表示する確認ダイアログ等で毎回シーンをロードするのは非効率。

**拡張方針:** UICommon に `ShowDialog<T>(string prefabAddress)` メソッドを追加。Addressables から Prefab をロード → Instantiate → AddUIView し、RemoveUIView 時にプールに返却する。UIView / UICommon の既存インターフェースは変わらない。

### FE-3: Modal 内サブナビゲーション

現状 UI 単体での「戻る」は SceneDirector の GoBack に依存。Modal 画面内のタブ切り替え等には対応していない。

**拡張方針:** SceneBase 内で独自の Stack を管理する。UICommon / UIView の設計には影響しない。

### FE-4: UI Toolkit 移行

**UI Toolkit 直行済み。** uGUI 経路は Debug 用レガシーとして暫定維持。§6.8 の対比表に従い、UIView の抽象インターフェース（ViewIn/ViewOut/GetUILayer）は変えず、内部実装のみ UI Toolkit / uGUI で分岐する。

**UI Toolkit 側:** レイヤーコンテナ + `VisualElement` Insert、Blocker は `pickingMode` 制御
**uGUI レガシー側:** SetParent + SiblingIndex、Blocker Image
**変わらないもの:** ViewIn/ViewOut の async インターフェース、UILayer、UICommon の LinkedList 一元管理

## 6.16 バインディング契約と状態の所有権

MVVM + Behavior パイプライン（概念モデルは §6.17）を UIView 実装に落とすときの不変契約と、置換可能な実装詳細の境界を定める。

### 状態の 4 分類と所有者

「Stable State か Visual State か」の 2 分類では不足する。View の射影として ViewModel が持つべき状態が存在するため、以下の 4 分類とする。

| 分類 | 定義 | 例 | 所有者 |
|---|---|---|---|
| ドメイン Stable State | ある瞬間に真である事実（ドメイン由来） | `Hp`, `IsOpen` | ViewModel（R3 `ReactiveProperty`） |
| プレゼンテーション Stable State | View の射影として導出される事実。時間軸を含まない | `IsPromptVisible`, `SelectedTabIndex` | ViewModel（R3 `ReactiveProperty`） |
| Visual State | 遷移中に毎フレーム変化する表示値 | `Opacity`, 表示中 HP（Model は 80 でも表示は 93） | **BehaviorRunner が統括**（Model は知らない） |
| 要素ローカル一時状態 | 入力に付随する一瞬の状態 | hover / focus / pressed | UI Toolkit 擬似クラス（誰もモデル化しない） |

**判定基準は「その値は時間軸を含むか」の一つだけ。** ある瞬間の事実として snapshot できるなら ViewModel が持ってよい（プレゼンテーション射影を含む）。遷移の途中でしか意味を持たないなら Runner が唯一の責務者である。ViewModel に Visual State を持たせると、設計原則 1（収束不変条件: 静止時の表示値は Stable State から一意に導出される）が検証不能になり、画面固有の遷移中フラグ復活と同型の失敗に至る。

Visual State の**表示上の実体**は Behavior が `VisualElement.style` へ適用する値である。`BehaviorRunner` は実行・割り込み・収束を統括し、`VisualStateStore` は FromCurrent 等の割り込みに必要な値を記憶する補助ストアである。全 style 値を Store に複製して正本を二重化してはならない。

### 不変契約（今固定するもの）

1. **ViewModel は Stable State（ドメイン + プレゼンテーション射影）のみを保持する。** `VisualElement` を参照せず、Visual State を持たない（E-7）
2. **要素取得とバインドは `OnRootCreated` に閉じる。** `VisualElement` または `BehaviorRunner` に触れる `IDisposable` は必ず `UIToolkitView.Track` で View 寿命へ登録する（E-8）
3. **レイアウト・見た目の規則は UXML / USS が権威。** C# は動的な値の適用のみを行う。UXML が直接指定できない生成 Root への一度だけの class 接続は例外として許容する
4. **時間を伴う変化は BehaviorRunner が担当し、Visual State の唯一の責務者である**

### 置換可能な実装詳細（暫定標準: `Q()`）

要素取得の手段（`Q()` / 生成コード / Binding DSL）は上記 4 契約を満たす限り View 内部の実装詳細であり、後から置換できる。現時点の暫定標準は `Q()` とし、以下を規約とする。

- 呼び出しは初期化時（`OnRootCreated`）のみ。フレーム毎の `Q()` は禁止
- name は定数で管理し、取得失敗は即例外（fail-fast）
- UXML で静的な Surface を明示する View（例: `OutGameBackgroundView`）は、その Surface を初期化時に一度だけ取得する。class や `picking-mode` は UXML 側に置く

### 置換のトリガー

以下のいずれかを観測したら、UXML Binding DSL または Source Generator による Binder の Vertical Slice を撤退ライン付きで実施し、`Q()` 標準の継続可否を判定する。

- 実画面が 3 を超え、かつ 1 View あたりの配線コード（`Q()` + Bind）が 20 行を超える View が常態化した
- 要素 rename に起因する実行時例外（fail-fast の発火）がリリース前検証で繰り返し検出された

置換対象は要素取得の実装のみであり、不変契約 4 条は据え置く。

### 寿命・通知の境界

`UIToolkitView` の破棄順序は **View 寿命の購読・Runner → ViewModel → Root → `OnViewDestroy`** とする。派生 View の `OnViewDestroy` は `IDisposable` の主な解放場所ではなく、C# event の対称な `-=` など追加クリーンアップ専用である。

| 対象 | 所有寿命 | 集約先 |
|---|---|---|
| `BindText` / `BindClick` / `BindVisible`、VisualElement を更新する購読、`BehaviorRunner` / `BindTransition` | View | `UIToolkitView.Track` |
| `ReactiveProperty`、ViewModel が持つ Domain / 外部 I/O 購読 | ViewModel | `ViewModelBase.Disposables` / `DisposeCore` |
| Scene フロー用の View outbound event | Scene | `OnLoadedImpl` で `+=`、`OnPreUnLoadedImpl` で `-=` |

Scene は View の public outbound API だけを参照する。View は ViewModel の通知を Scene 向け event として facade するか、ViewModel を読み取り専用公開するかのどちらか一方を選ぶ。現フェーズの `ConfirmDialogView` は前者を参照実装とする。

## 6.17 Behavior パイプライン — 状態と時間の分離

§6.16 の契約が「なぜその形なのか」を決めている概念モデル。実装は `Scripts/Runtime/UISystem/Behaviors/`（`BehaviorRunner` / `InterruptPolicy` / `TransitionBinder`）にある。

### 中心にある一つの区別

> **状態（State）と時間（Transition）は別物である。**

`Closed` → `Opening` → `Opened` → `Closing` という状態を持ちたくなるが、`Opening` / `Closing` は状態ではなく**時間を伴う変化**である。本設計が状態として持つのは `Closed` / `Opened` だけで、その間の変化は Behavior が担当する。

| 概念 | 定義 | 例 |
|---|---|---|
| **Stable State** | ある瞬間に真である事実。時間・演出を含まない | `IsOpen`, `Selected`, `Hp`, `Visible` |
| **Transition** | Stable State 同士の変化。時間を持つ | `Closed → Opened`、`100 HP → 80 HP` |
| **Behavior** | Transition の表現。合成可能な部品 | `TweenNumber`, `Shake`, `Flash`, `PlaySE` |

この分離の実利は、**ゲームロジックが Stable State だけを見て判断できる**ことにある。`if (Inventory.IsOpen)` で十分になり、「開きかけ」を条件分岐が気にしなくてよい。

### パイプラインと合成

Behavior は `Context → 副作用 → Context` を行う部品として直列に実行される（Middleware と同型）。

```
UIContext → Behavior → UIContext → Behavior → UIContext
```

部品なので合成できる。

```
HitEffect      = Tween + Flash + Shake + PlaySE
CriticalEffect = HitEffect + CameraShake + SlowMotion
```

### 割り込みポリシー（3つだけ）

遷移中に次の遷移が来る場合を `BehaviorRunner` が引き受ける。**Model は割り込みを関知しない。**

| ポリシー | 動作 |
|---|---|
| `Restart` | 実行中をキャンセル → **最終値へスナップ** → 新規実行を最初から |
| `FromCurrent` | 実行中をキャンセル（スナップしない）→ Visual State に残る現在値を OldValue として差し替え → 新規実行 |
| `Rewind` | 実行中をキャンセル → `IRewindableBehavior` を逆再生。非対応 Behavior は `Restart` にフォールバック |

ブレンド・即時終了などは提供しない。**逆再生の起点は常に現在の style 値を読む**（`startFromCurrent`）。これは `Rewind` に限らず、割り込み後の後続遷移すべてに効く一般則である。

### 収束不変条件

**静止時の表示値は、Stable State から一意に導出される。** 割り込みが何回連鎖しても、外部キャンセルが入っても、Dispose された後でも、最終的な表示は最後の Stable State と一致する。これは §6.16 の不変契約 1（ViewModel に Visual State を持たせない）を検証可能にしている条件そのもので、EditMode テストで固定してある（`BehaviorRunnerConvergenceTests` 他）。

### 三つの契約

| 種類 | 内容 | 権威 |
|---|---|---|
| Layout Contract | 何を表示するか | UXML |
| Data Contract | 何を Binding するか | コード API |
| Behavior Contract | どう動くか | コード API（ScriptableObject は直列化表現にすぎない） |

### 担当しない領域

| 領域 | 担当 |
|---|---|
| 入力認識（長押し・ドラッグ・スワイプ） | UI Toolkit の Manipulator。確定結果だけを Command / Stable State として ViewModel へ流す。連打抑止も Command 層（`CanExecute` / `IsTransitioning` 購読 / Modal Blocker） |
| 部品間協調（「A の ViewOut 完了を待って B を ViewIn」） | Scene 層が UniTask で await する命令的コード。オーケストレーションは本質的に命令的であり、これは設計の敗北ではない |
| 連続追従（毎フレーム変化する値） | 未実装。`Pairwise` による Transition 検出は離散変化が前提で、毎フレーム FromCurrent 割り込みを起こすのは不適切。常駐型 Behavior（Follow / SmoothDamp 相当）を別プリミティブとして扱う |

**境界の嗅覚:** Scene 層が遷移中フラグや Visual State を持ち始めたら、それは Runner へ移すべき責務が漏れているサインである。Scene が持ってよいのは順序の記述だけ。
