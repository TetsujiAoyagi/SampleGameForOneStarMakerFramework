# 29. UI エフェクト合成（非UIレンダラの描画順統合）

## 1. 一文

パーティクル・Live2D・Spine といった**非UIレンダラを、UI ツリーの任意の深度に挟む**要求（以下 **B**）に、**単一パネル構造を壊さずに**答えられるかを検討する。パフォーマンス絶対の指針の下で、案を1つに絞らず**実機検証で分岐する判断記録**として残す。

本章は方針を確定していない。§8 の検証が終わるまで実装に着手しない。

---

## 2. A と B の分離

「UE の Slate 相当が欲しい」という発想には、**2つの別要求が混ざっている**。混同したまま議論すると UseCase が特定できないため、最初に分離する。

| | 要求 | 典型例 | 解 | 本章の扱い |
|---|---|---|---|---|
| **A** | 大量の単純要素を安く描く | 画面空間マーカー、ネームプレート、ダメージ数字の群 | UITK `generateVisualContent` に自前ジオメトリを積むホスト | **対象外** |
| **B** | **非UIレンダラを UI 描画順の任意深度に挟む** | 2Dキャラを最前面、エフェクトはその後ろ、さらに UI 枠 | 本章で検討 | **対象** |

**A は本章で扱わない。** A の要否は設計論では決まらず、次の1点の計測でのみ決まる:

> プール済み `VisualElement` を N 個、`style.translate` のみ更新して破綻する N はいくつか。

UITK はレイアウト・スタイルを触らない限り transform の高速パスに乗るため、素朴な実装で数千個まで耐える可能性がある。**耐えるなら A の専用機構は不要。** 計測せずに A の基盤を作らない。

B は A の解（自前バッファ）では解けない。理由は §3 を参照。

---

## 3. なぜ B が難しいか

### 3.1 順序体系が別

`ParticleSystem` は `ParticleSystemRenderer`、すなわち **`Renderer`**。描画順はカメラのレンダーキューと sortingLayer / sortingOrder で決まる。一方 UITK の Panel と uGUI の Canvas はその外側で描かれる。**別の順序体系に属しているため、原理的に互い違いにできない。**

Live2D Cubism / Spine も同様に独自の Renderer を持つため、同じ問題に属する。B は「パーティクルの問題」ではなく「**非UIレンダラ一般の問題**」である。

### 3.2 UITK にノード単位のマテリアルが無い

`generateVisualContent` の頂点は `UnityEngine.UIElements.Vertex`（position / tint / uv）固定で、**マテリアル・シェーダを指定できない**。

ただし**加算合成については抜け道がある可能性が高い**。§6.1 を参照。ここが本章最大の分岐点。

### 3.3 ソートスロットが1つしかない

現構造は **単一 `PanelRenderer` + 単一 `UISystemPanelSettings`**、6つの UILayer は1つの root 内のコンテナ（[06-ui.md](06-ui.md) §6.4）。UI 全体でソートスロットが1個であり、**帯を挟む場所が構造的に存在しない**。

## 4. 前例

B は本プロジェクト固有の悩みではなく、両エンジンに共通する既知の穴である。

| 環境 | ノード単位マテリアル | B の解 |
|---|---|---|
| UE (Slate / UMG) | ○（Slate Brush にマテリアル） | Niagara は UMG に載らない。`Niagara UI Renderer` 等のサードパーティプラグインが定番 |
| Unity uGUI | ○（`Graphic.material`） | `UIParticle` (mob-sakai)。`ParticleSystemRenderer.BakeMesh` で焼いて `CanvasRenderer` に流す |
| **Unity UI Toolkit** | **×** | **既製の解が無い** |

**重要:** UE に Slate があっても B は解けていない。したがって「UE には Slate がある」は B を作る根拠にならない。Slate が答えているのは A（自前ペイント）であり、B ではない。

両エンジンで成立している唯一の形は共通していて、

> **エフェクトの出力を、UI 自身の頂点系に焼き込む**

である。本章の案A（§7）はこの形をそのまま UITK に持ち込むもの。

---

## 5. 要件の粒度

B の要求は「実行時に任意の深度へ動的にソートする」ことではない。

「エフェクト → 2Dキャラ → エフェクト → UI枠」というスタックは、**画面ごとに作家が決め打ちする固定順**であり、実行時に入れ替わらない。したがって必要なのは動的ソート機構ではなく、

> **UI ツリーの任意のノードが、エフェクトを持てること**

だけである。順序は UI ツリーが既に持っているものをそのまま使う。この絞り込みにより、要求は当初の想定よりかなり小さくなる。

## 6. 原則と、検証すべき前提

### 6.0 原則

**パフォーマンスが絶対の指針。** これは動かさない。

一方で **「単一パネル維持」は原則ではなく、パフォーマンス原則から導かれた帰結（の推定）**である。分割コストが実測で小さいなら、分割も選択肢に残る。本章は「単一パネルを守ること」を目的にせず、各案のコストを実測して順位づけする。

ただしパネル分割には、実測しても消えないコストが2つある。

| 分割コスト | 内容 | 性質 |
|---|---|---|
| 動的アトラスの複製 | 動的アトラスは `PanelSettings` 単位。帯ごとにアトラスが生え、同じスプライトが複製される。テクスチャメモリが帯数倍 | 性能。実測対象 |
| **Blocker がパネルを跨がない** | ピッキングはパネル単位。[06-ui.md](06-ui.md) §6.3 の「Modal/Dialog 表示時に透明 Blocker 自動生成」は、分割した瞬間に契約として成立しなくなる。帯ごとに Blocker を複製・同期する必要がある | **正しさ。測っても消えない** |

### 6.1 最大の未知数（1）— パネル合成は premultiplied alpha か

**加算ブレンドを出せるか否かは、この1点に帰着する。**

premultiplied alpha（`Blend One OneMinusSrcAlpha`）に **alpha = 0 / RGB > 0** の頂点を流すと

```
dst = src.rgb * 1 + dst * (1 - 0) = src.rgb + dst
```

となり、**追加シェーダなしで厳密な加算合成**が得られる。Spine / PIXI / Cocos の加算スロットが専用シェーダ無しで動くのと同じ原理。`Vertex.tint` のアルファを 0 にするだけなので、`generateVisualContent` の枠内で完結する。

成立条件は2つ:

1. UITK のパネルブレンドが `One OneMinusSrcAlpha` であること
2. UI シェーダがフラグメントで `col.rgb *= col.a` を**していない**こと（していると RGB が 0 に潰れて何も出ない）

**2 が踏み絵。** 通れば案A・案C' から「アルファブレンド限定」の制約が消え、両案とも実質無制約になる。検証の最優先（**V0**）。

### 6.2 最大の未知数（2）— `PanelRenderer` はソートに参加するか

`UIDocument` は Unity 6.5 で obsolete となり、`PanelRenderer` へ移行済み（[06-ui.md](06-ui.md) §6.7 注記）。

**`PanelRenderer` がシーン上の `Renderer` としてソートに参加するなら、Panel / Canvas / ParticleSystem が同一の順序空間に入る。** その場合、B は焼き込みも RT も不要で解ける（**V1**）。

`PanelRenderer` は新しい API であり、ネット上の `UIDocument` 前提の情報は当てにならない。必ず実機で確認すること。

## 7. 選択肢

**現時点で順位を確定させない。** コスト欄の「実測待ち」は §8 の検証で埋める。

| 案 | 内容 | ランタイムコスト | 任意深度 | 制約 |
|---|---|---|---|---|
| **案0**<br>PanelRenderer の素のソート | `PanelRenderer` が Renderer としてソートに参加するなら、帯は sortingOrder を振るだけ | 追加ゼロ（成立すれば） | ○ | 成立するか不明。V1 で確定 |
| **案A**<br>頂点焼き込み | `ParticleSystemRenderer.BakeMesh` の結果を `generateVisualContent` に流す。パーティクルの position / color / uv は UITK `Vertex` に過不足なく写る | **バッチ増加ゼロ・パネル1枚維持**。bake の CPU 分のみ | ○ ツリーの任意ノード | V0 が通れば加算可。歪み・ソフトパーティクルは不可。テクスチャは帯ごと1枚（アトラス化必須）。`Allocate` 1回あたり 65535 頂点 |
| **案C'**<br>縮小 RT を任意深度に貼る | **パネルは1枚のまま**。パーティクルを小 RT（1/4 解像度、エフェクト矩形にクロップ）へ描き、その RT を任意深度の `VisualElement` に貼る | 小 RT 1枚 + 埋めるパス1本。1/4 解像度なら fill / メモリとも 1/16 | ○ | **RT 内部はマテリアル完全自由**（加算・歪み・ソフトパーティクル全可）。UI への合成の正しさは V0 に依存（premultiplied で描き premultiplied で合成すれば数学的に正しい） |
| 案B<br>パネル分割 + uGUI 帯 | UITK パネルを帯境界で割り、間に uGUI Canvas を挟む | 実測待ち（バッチ分断 + `Canvas.BuildBatch` + アトラス複製） | ○ | **Blocker の複製・同期が必須**（§6.0）。uGUI が一級市民に昇格する方針変更を伴う |
| 案D<br>非対応 | エフェクトは最前面／最背面の固定2帯のみ | ゼロ | × | 「2Dキャラの前後にエフェクト」が表現できない |

**案0 / 案A / 案C' のいずれかが成立すれば、B は単一パネルを保ったまま、方針変更なしに解ける**（uGUI は Debug レガシーのままでよい）。

案A と案C' は排他ではない。**軽い演出は案A（頂点焼き込み）、歪み等が要る重い演出は案C'（縮小 RT）** の併用が自然。

### 7.1 却下しないが優先しないもの

**擬似 Slate（汎用の自前バッファ描画ホスト）を B の解として作らない。** 頂点バッファを自由に書けるようになっても、それ自体では Live2D も歪みも解決しない。B に効くのは「焼き込み先」であって「バッファの自由度」ではない。A が必要になった場合に限り、A の文脈で検討する。

- A（大量の単純要素）の要否。§2 の計測が済むまで保留
