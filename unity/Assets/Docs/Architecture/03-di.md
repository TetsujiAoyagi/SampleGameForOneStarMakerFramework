## 3.1 基本方針

> **決定 (2026-07-06): DI コンテナは導入せず、手動 DI（コンストラクタ注入 + Factory での配線）を正式採用する。**
> 当初は VContainer への移行を予定していたが、Phase 1〜現在まで手動 DI で不足がなく、
> 利用者が単独である本プロジェクトではコンテナの学習・保守コストが利点を上回らないと判断した。
> サービス数の増加で Factory の配線が破綻し始めた場合に、この決定を再評価する。

- **Game 層のクラスはコンストラクタ注入のみ。** DI Attribute (`[Inject]`) は使用禁止。
- **依存の配線（コンポジションルート）は DependOnAll に集約する。** `AppInitializer` と `GameSceneFactory` が唯一の配線場所。
- **Game 層はコンテナ・リゾルバの類を一切知らない。** 依存はすべてコンストラクタ経由で受け取る。

## 3.2 コンストラクタ注入の規則

```csharp
// ✓ Game 層のクラス — Pure C#
public class InGameScene : SceneBase
{
    private readonly ISoundService _sound;
    private readonly IInputManager _input;

    public InGameScene(ISoundService sound, IInputManager input)
    {
        _sound = sound;
        _input = input;
    }
}

// ✗ 禁止: Attribute ベースのフィールド注入
public class InGameScene : SceneBase
{
    [Inject] private ISoundService _sound;
}
```

**利点:**
- 依存が型シグネチャで自明（コンストラクタを見れば全て分かる）
- `readonly` フィールドが使える（フィールド注入では不可能）
- コンパイル時の安全性（依存不足はコンパイルエラー）
- テスト時に `new` で直接インスタンス化可能

## 3.3 MonoBehaviour への依存注入

MonoBehaviour は `new` できないため、コンストラクタ注入は不可能。
**Initialize メソッドパターン（2フェーズ初期化）** を採用する。

```csharp
// MonoBehaviour は Initialize メソッドで依存を受け取る
public class PlayerView : MonoBehaviour
{
    private IInputManager? _input;

    /// <summary>
    /// SceneBase の OnInitialize から呼ばれる。コンストラクタの代替。
    /// </summary>
    public void Initialize(IInputManager input)
    {
        _input = input ?? throw new ArgumentNullException(nameof(input));
    }
}

// SceneBase 側で呼び出す
protected override void OnInitialize()
{
    var playerView = FindRootComponent<PlayerView>();
    playerView.Initialize(_input);
}
```

**ルール:**
- MonoBehaviour は `Initialize()` が呼ばれるまで動作してはならない。
- `Initialize()` は冪等ではない。2回呼ばれたら例外を投げる。
- MonoBehaviour への依存の受け渡しは SceneBase の `OnInitialize` で行う。依存の出所は SceneFactory がコンストラクタ経由で渡したものに限る。
