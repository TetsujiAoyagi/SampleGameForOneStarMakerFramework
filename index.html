同じ file を持つ 2 つの Content Directory を同時に登録すると何が起きるか

Unity 6000.6 の Content Directory を、中身が同じ content file を持つ 2 つ分登録して、Editor の Play の中で実測した記録です。対象は OneStarMaker（OSM）の配布単位の設計です。

範囲: 1 台の PC、Unity 6000.6.0f1、StandaloneWindows64、loose file（非圧縮）、Editor の Play（Domain Reload 無効）、小さな fixture。Player・archive・実データでは測っていません。「実体の数」は load の結果として区別できる UnityEngine.Object の数（相異なる EntityId）で、物理メモリの量ではありません。

問い

別々に build した 2 つの Content Directory A と B は、共通の texture・material・shader・prefab について、名前も sha256 も同じ file を持ちます（前のスパイクで確認済み）。では、両方を ContentLoadManager.RegisterContentDirectory で登録したら、

  1. その asset の実体は 1 つか、2 つか。
  2. 片方を登録解除すると、もう片方から載せて持っている物は壊れるか。

Unity の公開文書は「登録中の directory は登録の逆順に探索される」とだけ言い、この 2 つには答えていません。

答え

Loadable から load
1
両方の root から同じ prefab を load しても、prefab・material・texture は 1 つ
Scene の直接参照から load
2
A の Scene と B の Scene が参照する material・texture は directory ごとに別の実体
登録解除で壊れた case
3 / 7
Error の log は出ないまま、持っている参照が == null になる

登録はどちらの順でも成功し、同じ名前の file が重複していることを知らせる Warning も Error も出ませんでした。各 round を 2 回繰り返し、同じ値になっています。

登録解除の 7 case

case登録の順持っている物解除する側結果
U1A → BB の root の prefab（A の物は Release 済み）A（先）無傷
U2A → BB の root の prefabA（先）無傷
U3A → BA の root の prefabB（後）壊れた
U4B → AB の root の prefabA（後）壊れた
U5A → BA の Scene の RendererB（後）無傷
U6A → BA の root の prefab（B の物は Release 済み）B（後）壊れた
U7A → BA の Scene の Renderer（B の Scene は unload 済み）B（後）無傷

壊れた 3 case は全て「先に登録した側から Loadable で載せた物を持ったまま、後から登録した側を解除した」場合です。解除の直後（同じ frame）に prefab・Renderer・material・texture の参照が == null になり、Unity は何も log に出さず、解除された directory は登録の一覧から消えました。解除の後に、生き残った側の handle から同じ asset を load し直すことはできました。

設計への含意

共通の asset を各 directory に複製したまま両方を登録する形は、保存と配布を hash で 1 つにまとめても、登録の単位では共有されません。

  • Scene の直接参照の経路では、同じ asset の実体が directory の数だけできる。
  • 後から登録した directory の登録解除が、先に登録した directory から Loadable で載せた物を黙って壊す。

このため OSM では、共有する asset を共有の package に分けるか、登録の寿命を package の間で結びつけるかを、配布単位の設計（次のスライス）で決めます。

途中で分かった副産物

読める texture（isReadable）は .resS を持ちませんでした。 1024×1024・RGB24・非圧縮の読める texture は、.cf が 3,147,948 bytes（pixel の raw 3,145,728 bytes を上回る）で、layout の ContentLayout.json に、それを指す texture の項目がありません。256×256 の読めない texture は、普通に .cf と .resS に分かれました。最初の判定はこのせいで未判定になり、「同じ file」の条件を改めてから測り直しています（大きさと読める設定のどちらが効いたかは切り分けていません）。

どう測ったか

  • SampleGame を使わない fixture を固定 GUID で生成し、2 つの directory を別々に build。両方で共通物の file の名前と sha256 が一致することを layout から確かめてから使う。
  • 名前だけが同じで pixel の違う texture を正の対照にして、「同じ名前の別の実体を 2 つと数えられる」ことを先に確かめる。
  • round ごとに新しい Play に入り、開始時に登録 0 件・共通物の名前の物 0 件を確かめる。製品の native wrapper（UnityContentDirectoryBackend）を無改変で 2 つ持って登録する。
  • 登録解除は、呼び出しの直後・1 frame 後・Resources.UnloadUnusedAssets の後の 3 時点で、生き残る側の物を確かめる。偽 null を見落とさないよう == null で判定する。
  • テストの合格は「harness が最後まで動いた」ことだけを意味し、答えは record（JSONL）の観測の行から、事前に固定した判定の手順で読む。独立した別の監査（別ベンダーのモデル）も同じ答えを出した。

測っていないこと

Player、archive（圧縮）、3 つ以上の directory、Scene に置いた prefab instance、sprite atlas、audio・video、中身が違う同じ id の file、片方の directory の file が disk から消えた時、Domain Reload 有効の Play、process をまたいだ再現（2 回の繰り返しは同じ Unity process の中）。
