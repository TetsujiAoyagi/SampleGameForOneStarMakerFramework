## 1. A0 / question / alternatives

OSM offers `IAssetManagement` with explicit `AssetOwner`. Unity `AudioSource` already plays and stops one `AudioClip`. A direct caller-owned source is adequate for one caller; a small common fixed-voice adapter adds typed registration, bounded source reuse and one synchronous stop/clear rule. No consumer presently requires a new game BGM, and no middleware implementation proves interchangeability. The source branch offers one-based `SoundHandle`, a forwarding `SoundPlayer`, `ISoundBackend`, and `UnitySoundBackend.Register(AudioClip)`, but retains registered clips until host destruction and has no explicit release-order proof. Branch history predates current develop; do not merge unrelated deletions in its develop-relative diff.

This slice answers: **can an owner that holds all registered clips for the backend's lifetime use an optional fixed Unity native pool with allocation-free typed play, and end all native references synchronously before its asset handles are released?** The minimum to proceed is a native AudioSource binding/replacement/cleanup proof, exact borrower/owner contract, and a fixed-head C/C' result. No audible-quality conclusion follows from component state.

Alternatives: (1) direct AudioSource at every caller, viable but duplicates fixed pool and cleanup policy; (2) this backend-scoped adapter, adopted; (3) independent registration leases/Unregister, deferred until a concrete shorter clip lifetime needs it. A separate SampleGame session loop is a later consumer slice, not a gate for this primitive. `ISoundBackend` is an optional substitution seam, not a promise that CRI/Wwise work.

## 2. Frozen candidate public contract and observable acceptance

- Keep existing `SoundHandle`, `SoundPlayer`, `ISoundBackend`, `SoundVoiceRing`, and `UnitySoundBackend` API shape for this PR. `SoundHandle.Invalid` is zero; `IsValid` means structurally positive **only**. Successful `Register(AudioClip)` returns one-based increasing index local to that backend. A handle from another backend is caller misuse and can alias a clip; no global identity or token promise. Registrations append until `Dispose`; do not add `Unregister`, generation table, release callback, or new public inspection API. Reject registration overflow before integer wrap or mutation. `Register` on a disposed backend throws `ObjectDisposedException`; destroyed/null clip throws `ArgumentNullException` using Unity `== null`.
- The creator owns the backend and its host. The backend **borrows** `AudioClip`, does not load/release/destroy it, and all registered clips must remain alive throughout backend lifetime. Caller obtains them through `IAssetManagement` with `AssetOwner.Manual` and releases each `IAssetHandle<AudioClip>` only after `backend.Dispose`; `AssetOwner.App` is allowed only with an explicit teardown order that disposes backend before `ReleaseAll`. `Scene(id)` and `Bind(go)` auto-expiring owners are unsupported. `SoundPlayer` borrows the backend and never disposes it. Public XML comments state these restrictions and that all native calls are on Unity main thread.
- `Play(SoundHandle, float)` accepts finite linear volume and clamps it to `[0,1]`; NaN/±Infinity is rejected without ring advancement or mutation of a sounding source. Preserve source void return/no-op semantics for invalid input, unregistered/invalid handle, destroyed registered clip, externally destroyed host/source, and a disposed backend. An invalid handle must not evict a current voice. No exception allocation on the routine no-op path. Successful selection of a previously occupied source performs `Stop`, `clip = null`, then clip assignment, volume assignment and `Play`; pool selection is the existing oldest-slot ring. Actual audible output is not promised by `Play`.
- `Dispose` is idempotent. It marks disposed first, then synchronously `Stop` and `clip = null` on each surviving source, clears every clip table entry/reference and count, and only then destroys the backend-owned host; deferred Unity `Destroy` in play mode does not defer reference clearing. Late `Play` is a no-op. Constructor failure destroys the partially built host. Do not create another `AudioListener`. Unity destroyed-object tests use `== null`/`!= null`, not managed null shortcuts.
- At least two registered clips and a one-source pool demonstrate overwriting and cleanup; nonfinite gain and invalid handle preserve the prior source; destroyed clip, source and host paths do not throw or dereference dead Unity objects; repeated dispose and late play are inert. A caller-protocol spy verifies Dispose-before-Manual-release call order, but is labeled as a protocol fixture, **not** an `IAssetManagement` integration proof. Native EditMode creates actual `AudioClip`/`AudioSource`, inspects `clip` and `volume`, and checks stop/clear/host cleanup. Do not require `isPlaying == true` in headless Unity or infer listening.
