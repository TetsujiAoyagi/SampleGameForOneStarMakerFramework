# 外部モデルレビュー効率調査への独立評価 — Claude / Grok

> ステータス: **2026-09-01 に人間が採否を決定。残る実測項目の判断材料。**
> 対象は `docs/handoff/REVIEW_WORKFLOW_EFFICIENCY.md`（以下「調査記録」）。
> 本書は採否判断の根拠を残す一時記録であり、現在の Phase 契約の正本ではない。
> harvest 先: 普遍契約は `.agents/skills/osm-workflow/`、現在のモデル・CLI割当は git 管理外の `docs/agents/` へ反映済み。
> 削除期限: 次のスライスの Phase C で「推奨」1 と 4 を実行し、結果を見て採否を決めた時点。調査記録ごと `git rm` する。

調査記録に対して Grok 4.6 と Claude Opus 5 が独立に評価した。本書は Claude 側の評価を軸に、Grok と一致する点・分かれる点を明示する。

**両者の結論は同じ方向を向いている: 足りないのは新しい契約ではなく、既存の記録が呼び出し前に読まれなかったこと。** ただし根拠と処方はいくつか異なる。

実測値を残したことが最大の価値である。808 秒、resume 123 秒、tool calls 223、C' の input 2,311,351（cached 94%）は、感覚論よりはるかに使える。「モデルが遅い」ではなく mode 選択・子 agent・検査の重複・文脈再送・quota の事後確認へ分解できている点も正しい。

改善案の芯も当たっている。Phase A の遡及確認を Phase C に混ぜない、C' に C の疑念リストを渡さない、決定的検査をモデルに何度もやらせない、性能帯を落とす前にコンテキストと round trip を減らす。これらは方向として正しい。

## 一次資料の検証で判明した衝突

調査記録の診断のうち 2 件は、このリポジトリが既に持っている実測記録と食い違っている。

### 問題1 は mode ではなく出力形式の可能性が高い

観測コマンド（調査記録 §1）は `--output-format json` を使っている。しかし `docs/agents/cursor-agent.md` の「非対話実行の落とし穴（実測）」表には、これが既に載っている。

| 記録済みの症状 | 記録済みの原因 | 記録済みの対処 |
|---|---|---|
| `json` の `result` が進捗ナレーションだけ | 最終回答が出力されず、分析が `thinking` イベントに留まったまま終了する | `stream-json` で全イベントを拾う |
| 出力が空なのに exit 0 | `text` / `json` は中身が空でも `is_error: false` を返す | **初回から `stream-json`** を使う |

「`--mode plan` のため最終レビューではなく計画・途中経過で止まり、追加の resume が必要になった」という観測は、この既知症状と区別がついていない。観測された実行は、同じ文書が名指しで避けろと言っている出力形式を使っていた。

### 改善案1 は既存記録と正面から矛盾する

同文書のオプション表は `--plan` を「読み取り専用モード（解析・指摘のみ、編集しない）。**監査はこれで回す**」と定義している。改善案1（`--mode ask` へ変える）を採るなら、どちらかを書き換える必要がある。両方を残すと 2 箇所が食い違ったまま腐る。

### 同文書の規律にも反している

`docs/agents/cursor-agent.md` のコスト規律は「**未検証の仮説のまま本番を回さない。仮説はプローブで潰してから本番**」である。次に変えるべき変数は mode ではなく `stream-json` であり、これは実測済みで、追加コストがゼロで、変数を 1 つに絞れる。

## 223 tool calls は新発見ではなく既知シグネチャの再現

同じ文書に記録がある。

> エージェントが結論を出さずに正常終了 → 論点を詰め込むと探索でターン予算を使い切る（実測: thinking 497 件・ツール呼び出し 92 回で可視出力は進捗 5 行のみ）→ **1 ジョブの論点は 2 つまで。字数上限を課し、結論を先に書かせる**

今回は Phase A の遡及確認と Phase C を混ぜた（調査記録の問題3）結果、同じシグネチャが約 2.4 倍の規模で再現した。

**問題3 が原因で、問題2（子 agent の三重探索）は症状である。** 子 agent の全面禁止は原因の取り違えで、大きい差分での並列分割を潰す副作用がある。禁じるべきは未分割の再探索であり、agent の数ではない。Grok も同じ結論に達しているが、根拠はこの実測値のほうが強い。

## 結論 — 足りないのは契約ではなく到達経路

調査記録 §2 の 9 項目は、すべて既にどこかに成文化済みのルールの違反である。規則は 4 箇所に散っている。

| # | 置き場 | git | 内容 |
|---|---|---|---|
| 1 | `AGENTS.md` | tracked | 常時契約 |
| 2 | `.agents/skills/osm-workflow/` | tracked | Phase 契約。**C' へのアンカリング禁止もモデル非固定も既にここにある** |
| 3 | `docs/agents/workflow.md` | **untracked** | 体制表、セッション分割の実測、構造レビュー手順 |
| 4 | `docs/agents/cursor-agent.md` | **untracked** | CLI の落とし穴（実測）、コスト規律 |

**事故を防げた知識は 3 と 4 にあり、そこは git 管理外である。** worktree にも clone にも存在せず、tracked 文書から markdown リンクを張れば `tools/docs-audit.ps1` の検査1（リンク先が git に無い）で落ちる。`AGENTS.md` の「作業別の追加指示」が `.agents/skills/` しか案内していないのは、この制約の帰結である。

これが真因である。呼び出し側のセッションが 3 と 4 に到達する正式な経路が存在しない。

### 副次的に見つかった欠陥

**`docs/agents/` は `docs/README.md` の3層表にも `tools/docs-audit.ps1` の `$localTiers`（`docs/planning/` / `docs/reference/` / `docs/slides/` / `docs/debugstudio/`）にも登録されていない。** untracked（`.git/info/exclude`）なのに、方針文書も監査もその存在を知らない第 4 の置き場になっている。素のパス言及は検査2 をすり抜ける。

調査記録の主題とは独立に、単独で修正に値する。

2026-09-01 に `docs/agents/` を手元層と `$localTiers` へ追加し、この欠陥は解消した。Phase契約がそこへ依存しないよう、普遍契約は tracked な Skill に置いた。

## §4（モデル経路の利用者指定）の評価 — Grok と分かれる

Grok は「§4 が調査記録でいちばん危ない。`phases-and-handoff.md` の『モデル名を将来の固定割り当てとして書かない』と衝突するので、正本化せず手元メモか Issue に置け」とする。

**前半は正しいが処方が違う。**

`docs/agents/workflow.md` には既に体制表があり、A/B/C/C' の担い手が明記されている。さらに次の判断まで書いてある。

> **C' に別ベンダーを当てるのは意図的である。** 2026-08 までは A/B/C/C' が全て Claude 系で、C' の独立性が「別ベンダー」から「別世代」に落ちていた。（中略）**この配置を「Codex で統一したほうが速い」と崩さないこと。**

つまり、tracked な skill が意図的にモデル非依存で、untracked な手元層が実際の配置を持つ、という層分けが既に成立している。両者は衝突していない。役割が違う。

したがって §4 は危険なのではなく、**3 箇所目を作っている**ことが問題である。書くべきでないのではなく、既にある体制表へ統合すべきである。`.agents/skills/` へ入れてはならない点は Grok と一致する。

## 調査記録の弱点（Grok と一致）

- **指摘の分類が無い。** 効率を論じた文書でありながら、223 calls が何を新規に発見したかが書かれていない。「スクリプトで落ちるもの / 人が 10 分で見えるもの / モデルが初めて見つけた意味的欠陥」の分類が無いと、どのコストを残すべきか決まらない。拾ったなら書く。拾っていないなら、それ自体が「モデルを厚くするな」の根拠になる。
- **期限が期限になっていない。** 「採用して harvest した時、または不採用を決めて記録が不要になった時」は同語反復であり、作業台に残り続ける。
- **N=1、しかも type-move PR。** 型の所在移動・GUID 維持・facade・CellRect 一本化は、機械検査が大半で意味的リスクが狭い差分である。ここで出た数値から失敗経路が厚いスライスへ一般化してはいけない。「60〜80% 削減」は後で目標値として一人歩きするので落とすべきで、残すなら「同じ PR で A/B してから」だけにする。

## スクリプト化の順序 — Grok と分かれる

Grok は「決定的検査を LLM の外へ出すのが本体。これが最優先」とし、`git diff` / GUID 突合 / asmdef 差分 / 保護 YAML 差分 / 契約 grep / テスト XML 要約を一括で出すスクリプトを提案する。

**優先順位には反対する。**

`tools/docs-audit.ps1` の設計思想は「**実際に起きた3つの失敗だけを検査する**」である。このリポジトリは、起きていない失敗を検査に足さない流儀で来た。上記「指摘の分類」が無いまま GUID 突合や YAML 差分まで含む bundle を書くと、何も落とさない検査が増え、Phase C の手順だけが厚くなる。

分類が先、範囲決定が後。順序を逆にすると、調査記録が批判している「重複した検査」を今度はスクリプト側で作る。

判断抜きで hard gate にしやすいのは、編集した Unity `.cs` の `#nullable enable`、Unity 側の `record`、テスト内の `Task.Delay` / `Thread.Sleep` である。偽 null（`?.` / `??` / `is null` / `ReferenceEquals`）は対象が破棄されうる `UnityEngine.Object` か、ログ型は公開 API かの意味判定が必要なので、単純 grep は failure ではなく review flag とする。`GetInstanceID` は現在の `AGENTS.md` に明文化された常時契約ではない。

なお Grok の「root が 74 calls で bundle を組むならコストは移動しただけ」という指摘は正しい。bundle を作るならモデル抜きで完結すること。

## 評価時点の推奨（優先順）

1. **次の Phase C は変数を 1 つだけ変える。** `--output-format stream-json` にする。mode は `--plan` のまま。既存の実測済み対処であり、これで直れば改善案1 は不要になる。二つ同時に変えると、どちらが効いたか分からなくなる。
2. **Phase A の遡及確認を Phase C の依頼に混ぜない。** 既存規則「1 ジョブの論点は 2 つまで」の適用であり、新規ルールは足さない。
3. **C' へ渡すのは HANDOFF・完全な diff・生のテスト結果・スクリプト出力のみ。** C の疑念リストは渡さない。ここだけは skill に**禁止の具体例**を 1 行足す価値がある。新しい哲学ではなく、既存文「Phase C の結論を正解として渡さず」の具体化として書く。例: 「C' プロンプトに facade / 旧 identifier / factory test gap のような候補を列挙しない」。
4. **指摘の分類を次の Phase C で取る。** それを見てからスクリプトの範囲を決める。
5. **§4 は `docs/agents/workflow.md` の体制表へ統合する。** `.agents/skills/` へは入れない。tracked 側のモデル非固定は維持する。
6. **`docs/agents/` を `docs/README.md` の3層表と `tools/docs-audit.ps1` の `$localTiers` に登録する。** 調査記録とは独立した小さな修正。

## 評価時点の harvest 可否

| 項目 | 判断 | 理由 |
|---|---|---|
| 決定的検査はモデルの外で一度だけ | 分類を取った後なら可 | 範囲が未確定 |
| C' に C の候補リストを渡さない（具体例として） | 可 | 既存文の具体化 |
| Phase を同一依頼に混ぜない | 可 | 既存規則の適用 |
| `--mode ask` への変更 | **不可** | `stream-json` を先に試すまで。既存記録と矛盾する |
| 子 agent の全面禁止 | **不可** | 原因の取り違え。並列分割を潰す |
| 60〜80% 削減 | **不可** | N=1、保証値でない。目標値として一人歩きする |
| GitHub Issue をレビュー正本にする | **不可** | 廃止した「正本表」を復活させる |
| §4 を `.agents/skills/` へ | **不可** | 体制表が既にある。3 箇所目を作る |

## 二者の評価が分かれた点

| 論点 | Grok 4.6 | Claude Opus 5 |
|---|---|---|
| 最優先の改善 | 決定的検査のスクリプト化 | `stream-json` への変更と、指摘の分類を取ること |
| §4 の扱い | いちばん危ない。正本化せず手元メモか Issue へ | 危険ではなく重複。既存の体制表へ統合する |
| 問題1 の原因 | mode 選択（調査記録の診断を踏襲） | 出力形式。既存の実測記録に対処まである |
| 真因 | 呼び出しが既存契約を破ったこと | 同じ。ただし破った理由は、契約が untracked 層にあって到達経路が無いこと |

一致した点: 子 agent 禁止は原因の取り違え、指摘の分類が欠けている、60〜80% は書くべきでない、Issue を正本にすべきでない、`.agents/skills/` を厚くすべきでない。

## 一言でいうと

**レビューが重いのではなく、既に記録済みの落とし穴に、記録を読まずに落ちた。** その記録が git 管理外にあって呼び出し側に届かない構造こそが直すべきもので、ワークフロー文書を厚くする段階ではない。
