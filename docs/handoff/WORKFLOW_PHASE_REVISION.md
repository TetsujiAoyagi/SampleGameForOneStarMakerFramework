### 論点 1: 取り直しの範囲と順序

**1a. 経路宣言による流用（推奨）**

- before（R1）: implementation head が変われば、全ての判定 evidence を新 head で取り直す。
- after:
  - A1 で、判定必須の証拠を 2 種に分ける。**常時取り直し**（offline suite、全 EditMode 回帰、contract-audit 等。安価で最終 head で必ず実行）と、**流用可能な高コスト証拠**（実 R2、Player Build、人間の観察等。不可逆・高コスト・残置を伴うもの）。
  - 流用可能な証拠ごとに **証拠経路** を A1 で宣言し A3 で凍結する。証拠経路は、その証拠が実行する file の集合（glob）で書き、間接に読み込む module・設定・transport を含める。宣言の無い証拠は流用不可（既定は取り直し）。
  - head が変わったとき、**検証済み head から新 head への `git diff --name-only` と証拠経路の交差が空**であれば、その証拠を新 head の判定に流用できる。交差判定は機械検査とし、判定 C より前に出力して evidence bundle と C′ の blind bundle に入れる（現行の「判定 C より前の機械検査」の枠に収まる）。
  - 交差が 1 件でもあれば取り直す。「触れたが経路の意味は変わらない」という意味判断による流用は認めない。
  - 流用元の head は公開済み（push 済み）で到達可能でなければならない（論点 5 と結び付く）。
- 影響する文書: review-evidence.md（「対象を固定する」「判定後の head 変更」「発見 C と判定 C」）、phases-and-handoff.md（「レビュー証拠と C′ の盲検性」末尾）、handoff-template.md §5（証拠の 2 分類と証拠経路の欄）。
- 残す安全性: 未検証の GO を出さない（経路に触れる変更は必ず取り直す。判断は機械で、宣言の外は fail-closed）。安価な回帰は最終 head で必ず実行する。
- 捨てる手順: 経路に触れない head 変更での高コスト証拠の取り直し（PR #119 の 4 回目に当たる）。
- 失うもの・リスク: 証拠経路の宣言漏れ（間接依存の見落とし）で、触れているのに交差が空と判定される。緩和: A2 のアーキテクチャゲートで宣言を確認し、C′ は宣言の妥当性も監査対象にする。
- 後続へ送る問い: 交差判定 script を tools に置くか（U8）。

**1b. 不可逆・高コスト検証を C′ の収束後に 1 回（推奨・owner 方針）**

- before（R2）: 実 R2 等は判定 C で実行し、その後の C′ の差し戻しで head が変われば再実行する。
- after: 順序を「判定 C（常時取り直しの証拠で GO 候補を確認）→ C′ → 両方で阻害する指摘が無くなった head で高コスト証拠を 1 回取得 → **最終証拠ラウンド**」とする。
  - 高コスト証拠の手順と期待値は A3 で凍結し、可能な限り機械判定にする（PR #119 の AC23 は期待する削除 ID を receipt から機械で算出する形で、既にこれに近い）。
  - 最終証拠ラウンドでは、判定 C と C′ の双方が、新たに加わった生証拠だけを見る（C′ は blind のまま、凍結済み手順・期待値と生証拠の照合に限る）。ここで実装欠陥が出たら通常の差し戻しに戻る。
  - 例外: 高コスト証拠でしか再現しない欠陥の確認は、現行どおり理由と範囲を記録して限定実行できる。
- 影響する文書: review-evidence.md（「発見 C と判定 C」の順序）、SKILL.md Phase C／C′、handoff-template.md §5。
- 残す安全性: 高コスト証拠は最終 head で取得し、C と C′ の両方が確認する。
- 捨てる手順: C′ 収束前の高コスト証拠の取得。
- 失うもの・リスク: C′ が高コスト証拠の生結果を見ながら全体を監査する機会を失う。高コスト証拠で初めて見える欠陥の発見が最後に遅れる（その場合は 1 往復増える）。

### 論点 2: C′ の blind をどこまで緩めるか（P2）

各案で得るものと失う独立性:

| 案 | 内容 | 得るもの | 失う独立性 | 推奨 |
|---|---|---|---|---|
| 2A | owner の裁定（不採用・後続への移送と、その理由）を、C の所見と区別した「凍結済みの決定」として C′ に渡す | 不採用済み指摘の再指摘を防ぐ（F2 の 3 回） | 裁定の存在が「どこが争点だったか」を示し、探索先の誘導になる。裁定そのものへの独立な異議の機会が減る | 採用 |
| 2B | C の結論（GO/FAIL）だけを隠し、所見の ledger は見せる | 収束は最も速い | 大きい。C′ が C の探索範囲にアンカリングされ、C の第二意見になる。C の見落としを独立に拾う目的を失う | 不採用 |
| 2C | 2 巡目以降は、前巡の C′ 指摘の解消と、修正差分の回帰に限る | 発見 C と同じ収束性（F3）。毎巡初見の全体監査をやめる | 1 巡目に見落とした未変更部分の欠陥を、後の巡で拾う機会を失う。未変更部分は 1 巡目に同じ凍結仕様で監査済みなので損失は小さい | 採用 |
| 2D | blocker を「凍結済みの安全性を破る具体的な順序（入力・状態・操作の列）を示せるもの」に限る | AC の文言の隙間だけの指摘が blocker にならない（F2 の AC21・AC2/AC4(a)・AC7） | 独立性ではなく判定の感度を落とす。具体的な順序を組めない微妙な欠陥が後続へ回る | 採用（論点 3 と組にする） |

推奨の組合せ（2A＋2C＋2D）の具体:

- before（R3・R4）: C′ には発見 C・判定 C の結論・指摘・誘導的説明を渡さない。owner の裁定も渡らない。毎巡全体を監査する。
- after:
  - **凍結済みの決定（2A）:** owner が A3 後に下した裁定（AC の解釈、不採用、後続への移送）を、理由とともに「決定記録」として Phase A snapshot の追補に置く。C′ はこれを凍結済み条件と同格に読む。決定記録には **owner の結論と理由だけ** を書き、誰がその指摘を出したか（C か C′ か）、C の推論・疑念候補は書かない。C′ は決定記録が凍結済みの安全性（不変条件、論点 3）を破る具体的な順序を示せる場合に限り、決定への異議を blocker として出せる。それ以外の異議は後続への入力として記録する。
  - **AC の解釈の裁定:** 文言の隙間が見つかったとき、実装と契約を変えない解釈の確定は、Phase A の新しい revision を開かず決定記録で行える。実装・契約・受け入れ境界が変わる場合は従来どおり A revision。
  - **2 巡目以降（2C）:** 前巡の C′ 指摘ごとの解消確認と、前巡の head から新 head への差分（修正差分）が触れる経路の回帰に限る。差分の外の新規指摘は、2D の具体的な順序を示せる場合だけ blocker とし、それ以外は後続へ。
  - **blocker の具体化（2D）:** C′ の blocker は、違反する凍結済み条件・不変条件に加え、違反に至る具体的な順序を記録する。
  - 上限 3 巡は維持する。
- 影響する文書: SKILL.md Phase C′、review-evidence.md（「Phase C′ の blind audit bundle」と C′ の入力）、phases-and-handoff.md（「レビュー証拠と C′ の盲検性」「意思決定境界とスコープ停止」）、handoff-template.md（§2 に決定記録、§8 に巡ごとの範囲）。
- 残す安全性: C の結論・指摘・疑念候補は引き続き C′ に渡さない。C′ は新規 session・B/C と異なるモデル（AI 担当の場合）。1 巡目は全体を初見で監査する。
- 捨てる手順: 不採用済み指摘の再審理、2 巡目以降の全体初見監査、文言の隙間だけを根拠とする blocker。
- 後続へ送る問い: 決定記録を Phase A snapshot の追補にするか、別の固定 file にするか（実装時に決める。追補なら snapshot の hash が変わる点を review-evidence の manifest 規則で扱う）。
- §4 C 依存: 緩め方は依存しない。Cloud Agent が C′ を担うには blind bundle の取得が必要で、依存する。

### 論点 3: 最低条件・AC の書き方

- before（R5）: 進める最低条件と、その詳細である受け入れ条件を列挙する。blocker は凍結済み条件または常時契約への違反。
- after:
  - 進める最低条件を **不変条件**（起きてはいけないこと。例: 候補でない Build を消さない、確認できない削除を削除済みにしない）と **成立条件**（起きなければならないこと。例: N を超えた最古の Build が削除される）に分けて先に書く。
  - 受け入れ条件は、各不変条件・成立条件の **検証例** として書き、どの条件を検証するかを紐付ける。不変条件ごとに少なくとも 1 つの AC（失敗経路を含む）を持つ。
  - 判定（C・C′ とも）: blocker は、不変条件の違反（具体的な順序付き、論点 2D）、成立条件の不成立、AC の失敗、常時契約の違反のいずれか。AC の文言の隙間で、どの不変条件にも違反しないものは blocker ではなく、決定記録での解釈確定（論点 2）か後続への入力にする。
- 影響する文書: phases-and-handoff.md（「意思決定境界とスコープ停止」）、handoff-template.md §2、SKILL.md Phase A／C／C′ の該当文、review-evidence.md「Phase C の入力」。
- 残す安全性: 失敗経路の検証（不変条件ごとの AC 必須）。凍結済み条件以外での scope 拡張の禁止。
- 捨てる手順: AC の文言の完全性を判定の前提にすること。
- 失うもの・リスク: 不変条件が抽象的すぎると判定が争点化する。緩和: 不変条件は観測可能な語で書き、A2 で「各不変条件を破る順序を 1 つ挙げられるか」を確認する。
- 適用範囲: A3 以降に新しく A1 を始めるスライスから。進行中・凍結済みのスライスは書き直さない。

### 論点 4: PR を状態の窓口にする（P1 前提）

- before（R7）: PR 本文の更新時期・担当の規定が無い。A3 時点の本文が残る（F4）。
- after:
  - PR 本文の先頭に固定形式の **状態ブロック** を置く。項目: 現在の Phase と状態、凍結した Phase A の revision と commit、implementation base／head、次の担当（Phase と役割。モデル名ではない）と次の作業、HANDOFF の path、Evidence 取得案内の状態（未生成／未保存／引渡し未完了／確認済み。reference と hash の実値は書かない）、未決事項。
  - タイトルはスライスの成果を表す名前にし、「Phase A draft」等の Phase を入れない。Phase は状態ブロックにだけ書く。
  - 更新は **各 Phase の出口の担当** が、その Phase の最後の手順として行う（A3 凍結、B 完了、判定 C 完了、C′ 完了、D）。Phase D の担当はマージ前に、状態ブロック・本文の要約が最終 head と一致することを確認する。
  - C′ 完了まで、状態ブロックと本文には判定 C の結論・指摘を書かない（「判定 C 完了」の事実だけ）。C′ の担当は PR 本文を入力にしない（現行どおり）。C/C′ の結果は Phase D で本文に要約する。
  - 正本は HANDOFF §0 のままとし、状態ブロックはその写しの最小集合にする（同じ事実の二重化を最小にする）。
  - Cloud Agent は、リモートのブランチ（HANDOFF）と PR の状態ブロックだけで、今の Phase、固定 head、次の担当を判断できる。証拠の閲覧は §4 C に依存し、未対応の間は「証拠の取得はローカル担当」と状態ブロックに書く。
- 影響する文書: SKILL.md（「作業開始時」「完了」、各 Phase の出口）、handoff-template.md（状態ブロックの雛形を追加）。
- 残す安全性: C′ の blind（PR 本文に所見を出さない）、公開面に内部台帳・機微な path を出さない。
- 捨てる手順: なし（新規の更新手順を足す）。
- 後続へ送る問い: 状態ブロックを HANDOFF §0 から script で生成して二重化を機械的に防ぐか（U8）。

### 論点 5: 中間 commit と入力版 hash（P1 前提）

- before（R6）: 公開後は 1 ラウンド 1 修正 commit、未 push の中間 commit は整理する。A2 の入力版は commit hash で記録していた（PR #119 は sha256 も併記）。
- after:
  - **Phase A の HANDOFF revision の commit は整理の対象外** とする。A3 で push するので公開履歴になり、レビュー入力の記録として残す。整理の規則は B 以降の実装の試行錯誤 commit に限ると明記する。
  - A2 の入力版は **内容の sha256 を正**、commit hash を補助として記録する。履歴が変わっても、Phase A snapshot（Artifact Storage に保存）と内容 hash で入力版を照合できる。
  - **判定 evidence を取った head は push してから次の修正を積む。** 流用（論点 1a）の起点になる head が整理で消えないようにする。高コスト証拠の無い中間 head は従来どおり整理してよい。
  - 「整理で head が変わったら取り直す」は維持する（判定 evidence を取った head は整理しないので、この衝突は起きない）。
- 影響する文書: SKILL.md「PR公開後の差し戻しとGit履歴」、phases-and-handoff.md（A2 の入力版の記録）、handoff-template.md §5（A2 の入力版の欄）。
- 残す安全性: 判定に使った head の到達可能性、公開履歴を書き換えない、試行錯誤を PR 履歴に積まない。
- 捨てる手順: Phase A の commit の整理。

### 論点 6: 判定 C の照合 script の作り方

- before（R9）: 規定が無い。PR #119 では実行できない読取専用の担当が書き、実装担当が実行を代行して 4 往復した（F6）。
- 案:
  - 6a: 判定 C 担当に、ローカルの offline 実行を許す。対象は原記録の複製で、network・資格情報・Unity には触れない。
  - 6b: 照合 script を A1 で書き、A2 でレビューし、A3 で凍結する。判定 C は凍結済み script を実行し、出力形の B 適応（field 名等）だけを根拠付きで行う。
  - 6c: B が書いて合成 fixture で通し、判定 C がレビューする。照合の独立性（実装者が検査器を書かない）を失うので不採用。
- 推奨: **「実行できない担当に照合 script を書かせない」** を規則にする。判定 C の環境で offline 実行できるなら 6a、できないなら 6b。どちらも、原記録へ適用する前に、A3 で凍結した期待値を持つ **合成 fixture で一度通す**。
- 影響する文書: review-evidence.md（「発見 C と判定 C」の判定 C、検証経路の証拠）、phases-and-handoff.md（「検証経路の成立」）、handoff-template.md §5。
- 残す安全性: 照合は実装担当と独立した担当が書く。判定 C の offline 実行は network・資格情報・実 R2 に触れない（実操作は従来どおり承認済みの経路だけ）。
- 捨てる手順: 書いた本人が実行できない状態での往復。
- §4 C 依存: ローカル実行なら依存しない。Cloud の判定 C が原記録を読むには依存。

### 論点 7: 1 session で B・C・C′ を回さないための Phase 境界の引継ぎ

- before（R8）: Phase 境界では新しい session を使う。引継ぎの形式は規定が無い。PR #119 では B の session が C の実行と C′ の起動を担った（F8）。
- after:
  - **引継ぎ票:** 各 Phase の出口で、次の担当が会話履歴なしで始められる固定形式を HANDOFF §0 と PR の状態ブロック（論点 4）に書く。項目: 次の Phase、凍結 revision、base／head、入力（evidence・snapshot の取得案内の在処と状態）、必要な権限（Unity、実 R2、資格情報、sandbox 外実行）、停止規則、引き渡さないもの（C′ には所見を渡さない等）。
  - **実行担当と判断担当の分離:** 判断担当が実行できない場合（読取専用の外部モデル等）、判定必須テスト・高コスト証拠の実行は B の session ではなく、**判定 C 用に新しく開いた実行担当 session** が凍結済みのコマンドだけを実行し、生結果を判断担当に渡す。B の session は B の出口（引継ぎ票と push）で終える。
  - **Cloud Agent が引き継げる範囲:** B と発見 C（diff と offline 検査で足りる範囲）は、リモートのブランチと引継ぎ票から引き継げる。判定 C（Unity・実 R2・ローカル Evidence）と C′（blind bundle の取得）は §4 C が成立するまでローカル担当とし、引継ぎ票に明記する。
- 影響する文書: phases-and-handoff.md（「Phase の責任」末尾、「モデル選定と独立性」）、SKILL.md（各 Phase の開始・出口）、handoff-template.md §0。
- 残す安全性: C は B と異なるモデル、C′ の blind、Unity テストは Phase C の責任（`AGENTS.md`）。
- 捨てる手順: B の session による C・C′ の進行。
- §4 C 依存: 判定 C・C′ の Cloud への引継ぎは依存する。

### 論点 8（付随）: Evidence の保護名規則への対処（F7）

- after: review-evidence.md の「保存先とリモートへの配布」に、保護名規則に当たる非秘密 file（テスト fixture の `Credentials.json` 等）は梱包時に決まった規則で改名し、元の名前との対応表を bundle に収録する、と書く。保護名規則そのものは変えない（対象外）。
- 残す安全性: 秘密の非露出（保護名規則は維持）。改名は非秘密であることを送信担当が確認した file だけ。

### 選択肢の比較と採否の理由（A1 主担当の見解）

上の各案で採らなかった選択肢と、推奨を選んだ理由を論点ごとに残す。根拠は §1 の F1〜F8。

**1-① 証拠の流用**

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. 現状維持（head が変われば全部取り直す） | 却下 | F1 の 4 回目は削除経路に触れていないのに実 R2 を取り直し、object が 10 件増えた。安全性は増えず、不可逆なコストと残置だけが増えた |
| b. 判定 C が意味で判断して流用する | 却下 | 「影響しない」という判断そのものが新しい判定対象になり、誤れば未検証の GO になる。C′ が監査するには C の推論を見る必要があり、blind と両立しない |
| c. 宣言した経路と機械照合して流用する（1a） | 推奨 | 機械検査なので C′ の blind bundle に入る。宣言外は流用不可、1 件でも重なれば取り直しで、迷う場面は取り直しに倒れる。流用対象は高コスト証拠だけで、安価な回帰は最終 head で必ず実行する |

c で失うのは宣言漏れ（間接 import の書き忘れ等）への耐性。A2 のアーキテクチャゲートと C′ の監査で宣言を確かめる。漏れを許容できない証拠は宣言しなければ流用不可になる。

**1-② 不可逆・高コスト検証の時期**

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. 現状（判定 C の中で実行） | 却下 | PR #119 で head が変わった原因は C′ の FAIL だった。C′ より前に実 R2 を回すと、差し戻しのたびに無駄になる |
| b. C′ の収束後に 1 回だけ行い、最終証拠ラウンドを設ける（1b） | 推奨・owner 方針 | 順序で取り直しを防ぐ。AC23 のように期待値を A3 で機械的に凍結しておけば、最終ラウンドの照合は軽い |
| c. 判定 C で実行し、C′ 後の修正は 1-① の流用で対応 | 次点 | C′ の修正が経路に触れれば結局取り直しになる |

b で失うもの: C′ が 1〜2 巡目を実 R2 の生結果なしで監査すること。実 R2 でしか見えない欠陥の発見が最後になり、その場合は 1 往復増える。

**2 C′ の緩め方**

F2 の原因は、裁定を知らないことによる再指摘（3 回）と、毎巡の初見監査による新しい文言の隙間の指摘の 2 種類で、案ごとに効く対象が違う。

- **2A 採用:** 再指摘に効く。失うのは、裁定の存在が争点の場所を示すこと（探索の誘導）と、裁定への独立な異議の機会。owner の裁定は A3 の凍結条件と同じ「人間が決めたこと」で、C′ は凍結条件に異議を唱える役ではないため、損失は小さいと判断した。結論と理由だけを渡し、誰が指摘したかや C の推論は書かないことで、C の所見が裏口から入る経路を断つ。
- **2B 却下:** 収束は最速だが、C′ が C の探索範囲にアンカリングされ C の第二意見になる。C′ の存在理由（C が見なかった場所を見る）を失い、実質的にレビューを 2 件にするのと同じ。P2 の「緩める」の範囲を超えると判断した。
- **2C 採用:** 毎巡の新しい隙間に効く。F3 の発見 C はこの方式で 3 巡で収束した。C の所見は見ないままなので、独立性はほぼ失わない。失うのは、1 巡目に見落とした未変更部分を後の巡で拾う感度。未変更部分は 1 巡目に同じ凍結仕様で監査済みで、それを毎巡探すと F2 のように終わらない。差分の外でも 2D の順序を示せるものは blocker にできる。
- **2D 採用（論点 3 と組）:** 文言の隙間だけの FAIL に効く。PR #119 の C′ の残り 2 件は、どちらも具体的な誤削除の順序を示せなかった。失うのは独立性ではなく判定の感度で、微妙な欠陥は後続への入力に回る。単独では「どの安全性か」が曖昧なので、論点 3 の不変条件と組にする。

残す独立性の核: C の結論・指摘・疑念候補は渡さない、1 巡目は全体を初見で監査する、上限 3 巡を維持する。

**3 最低条件・AC の書き方**

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. 現状（最低条件と AC を列挙する） | 却下 | PR #119 は A2 を 5 巡しても、凍結後に AC21・AC2/AC4(a)・AC7 の隙間が出た。文言の完全化は収束しない |
| b. 不変条件と成立条件を先に書き、AC を検証例にする | 推奨・owner 方針（新規スライスから） | 判定の基準が「文言どおりか」から「不変条件を破るか」に変わり、違反の無い隙間は blocker でなくなる。2D の「安全性」をここで定義する |
| c. AC をより厳密に書いて隙間をなくす | 却下 | a の努力を Phase A へ前倒しするだけ |

b で失うもの: 不変条件が抽象的すぎると、破っているかが新しい争点になる。観測できる語で書き、不変条件ごとに失敗経路の AC を必須にし、A2 で破る順序を 1 つ挙げられるか確かめる。凍結済みスライスの書き直しは影響が大きいので、適用は新規スライスから。

**4 PR を状態の窓口にする**

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. 現状（規定なし） | 却下 | F4 が起きた |
| b. PR 本文を HANDOFF と同じ詳しさで毎回更新する | 却下 | 同じ事実が 2 箇所に置かれ、片方だけ直されて腐る |
| c. 最小の状態ブロックを本文の先頭に置き、Phase の出口の担当が更新する | 推奨 | Phase 境界でしか変わらない値だけを写すので、腐る面積が小さい。更新者を決めれば放置は Phase D で必ず検出される。Cloud Agent はブランチと状態ブロックで現在地が分かる |
| d. 状態ブロックを HANDOFF §0 から script で生成する | 後続（U8） | 効果は大きいが tools の追加になる。手で回して腐るなら script にする |

C′ 完了までは判定 C の結論を PR に書かない（blind の維持）。タイトルに Phase を入れないのは F4 の再発防止のため。

**5 中間 commit と入力版 hash**

衝突の原因は、目的の違う 2 種類の commit（実装の試行錯誤と、A2 レビューの入力記録）を同じ「中間 commit」として扱ったこと。P1 により Phase A の commit は A3 で公開履歴になる。

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. Phase A の commit も整理し、入力版は sha256 だけで残す | 却下 | レビュー入力を git で辿れなくなる |
| b. Phase A の commit は整理の対象外とし、入力版は内容 sha256 を正にする | 推奨 | 適用範囲を分けるだけで衝突が消える。履歴が変わっても Phase A snapshot と sha256 で照合できる |
| c. A2 入力版ごとに tag を打って push する | 却下 | tag が増え続け、別の清掃規則が要る |

追加: 判定 evidence を取った head は push してから次の修正を積む（1-① の流用元を整理で消さない）。

**6 判定 C の照合 script**

| 選択肢 | 独立性 | 判断 | 理由 |
|---|---|---|---|
| a. 判定 C 担当にローカルの offline 実行を許す | 保たれる | 推奨（実行できる環境なら） | 最速。原記録は非秘密のものに限る |
| b. A1 で書き A2 でレビューして A3 で凍結する | 保たれる（計画担当が書く） | 推奨（実行できない環境なら） | 出力形のずれは B 適応で根拠付きに直す |
| c. B が書き、判定 C がレビューする | 失う（実装者が自分の検査器を書く） | 却下 | 照合の独立性が目的なので本末転倒 |
| d. 現状（実行できない担当が書き、別担当が代行） | 保たれる | 却下 | F6 の 4 往復。原因は能力ではなく「書く人と実行する人が別」という構造 |

a・b とも、原記録へ適用する前に、期待値を凍結した合成 fixture で一度通す。

**7 Phase 境界の引継ぎ**

| 選択肢 | 判断 | 理由 |
|---|---|---|
| a. 現状（「新しい session」の規則だけ） | 却下 | F8 |
| b. 引継ぎ票と、実行担当・判断担当の分離 | 推奨 | 会話履歴なしで始められることが Cloud Agent の引継ぎ条件になる。B の session を push と引継ぎ票で終えれば、session 長によるコストも抑えられる |
| c. 人間が全 Phase を仲介する | 却下 | 人間の負担が増え、Cloud Agent の参加と逆行する |

**8 保護名規則:** 規則を緩める案は秘密の保護に関わるため対象外とした。非秘密と確認した file だけを改名し、対応表を収録する運用を採る。
