prefab を編集して build し直すと、Scene に古い prefab が残る

Unity 6000.6 の Content Directory の build は差分 build です。Scene に置いた prefab を編集して同じ project で build し直すと、Scene の出力は古い prefab のまま再利用されます。build は成功し、Warning も出ません。原因を切り分け、最小の再現を作り、cache を捨てずに済む回避を実測した記録です。

範囲: 1 台の PC、Unity 6000.6.0f1、StandaloneWindows64、loose file（非圧縮）、build は同じ Library。prefab は variant でなく、override が無く、unpack していない instance。Player の build、別の PC、実データでは測っていません。

きっかけ

前の記事で、取得した build（base）に手元で build した上書きを重ねれば上書きの版が読まれる、と分かりました。そこで OSM の製品の build 経路に「編集した asset の集合から、影響を受ける Scene と asset だけを上書きとして build する」機能を足し、Editor の Play で確かめました。

結果は、10 個の受け入れ条件のうち 9 個が成立しました。編集した texture を直接参照する Scene や、prefab を root として直接読む経路は、上書きの版で出ました。Scene に置いた prefab の instance（入れ子の prefab を含む）だけが、上書きから読んでも古い版のままでした。上書きの directory の中を調べると、その Scene の file は base と同じバイトで、新しい位置の値はどの file にもありませんでした。

原因

別の Editor process で build
古い
process のメモリの状態ではない
上書きでなく全体を build し直す
古い
上書き固有の問題ではない
CleanBuildCache の後に build
新しい
原因は Library の build cache

Content Directory の build は、出力の file ごとに build instruction を作ってハッシュを取り、前回と同じなら、前に書いた file を再利用します。Unity が Library/BuildHistory に残す trace を見ると、prefab を編集した後の build で、Unity は Scene の build 用 metadata を作り直していました。それでも Scene の instruction は「変更なし」と判定され、古い出力が使われました。

なぜ prefab の変更が Scene の判定に効かないのか。build した Scene は prefab を参照していないからです。Editor の Scene の file は「この prefab の instance で、差分はこれ」だけを持ち、Editor が開くたびに prefab と合成して見せています。build の時はこの合成の結果、つまりただの GameObject の集まりが Scene の出力に焼き込まれます。実行時に prefab の仕組みを持たずに済み、読み込みも速くなるからです。ところが差分 build の判定は Scene の file のバイトだけを見ていて、合成に使った prefab を見ていませんでした。

この不具合は上書きに限りません。「prefab を直して、同じ project で Content Directory を作り直す」だけで起きます。全部を作り直して丸ごと差し替える運用でも、build が同じ Library で走る限り当たります。正しくなるのは、cache が空の時（新しい checkout や CleanBuildCache() の後）だけです。

最小の再現

OSM を使わない、package を 1 つも持たない project で再現しました。C# は 2 file だけです。

  1. 子の位置が (1,2,3) の prefab と、その instance を置いた Scene を作って build する。出力は (1,2,3)。
  2. prefab の子を (4,5,6) にして保存し、build し直す。Editor で Scene を開くと (4,5,6)、Scene の file のバイトは変わっていない。出力は (1,2,3) のまま。build instruction は 4 個中、変更 0。
  3. BuildPipeline.CleanBuildCache() の後に build すると、(4,5,6)。

ただし CleanBuildCache() は全ての content の差分 build を捨てます。毎回これをすると、差分 build の利点のほとんどを失います。

回避: Scene に、焼き込む prefab のハッシュの印を持たせる

鍵が Scene の file のバイトなら、prefab が変わった時に Scene のバイトも変わるようにすればよい、という発想です。同じ再現の project で 3 通り試しました。

やり方正しさcachesource に残る差分
Scene に意味のない変更を入れ、build の後に戻す戻すと古い版に戻る—無し
build のたびに印の object を足し、build の後に戻す正しい毎回作り直し（object の内部 ID が毎回変わる）無し
印の置き場を 1 つだけ Scene に置き、build の直前にその名前を prefab のハッシュに書き換え、build の後に戻す正しい効く置き場の object 1 つ（一度だけ）

3 つ目の形で、prefab を v1 → v2 → v2 → v1 → v2 と進めたり戻したりして 5 回 build しました。5 回とも正しい版が出ました。作り直したのは prefab が変わった時の Scene 1 個だけで、同じ版の再 build と前の版に戻した build は、作り直しゼロで cache を丸ごと再利用しました。印の object には EditorOnly の tag を付けたので、build の出力には残りません。全 build の後、Scene の file は元のバイトに戻っています。

決め手は、印入りの Scene のバイトが「元の Scene + prefab のハッシュ」だけで決まることです。prefab が同じなら毎回同じバイトになって cache が当たり、prefab が変われば鍵が変わって作り直されます。build の後に戻すので、印の値を VCS に commit する必要もありません。

OSM での扱い

  • 上書きの build の計画は、この不具合のため不成立とした。逆引きの規則、登録の契約、重複の報告など、他の部分は実測で成り立った。
  • 回避は印の方式に決め、製品の build 経路に入れるのは次のスライスにする。入れ子の prefab、複数の Scene、build が途中で落ちた時に Scene を戻すこと、読み取り専用の file への手当てを、そこで決めて測る。
  • Unity へ報告するための最小の再現 project を用意した。

途中で分かったこと

  • Unity が Library/BuildHistory/<build>/BuildContentTEP.json に残す trace には、build instruction の変更数・再利用数や、どの asset の metadata を作り直したかが入っている。差分 build の挙動を調べる時の一次資料になる。
  • AssetDatabase.GetAssetDependencyHash は、prefab や texture を編集しても Scene の値が変わらなかった。依存の中身を表す値としては使えなかった。
  • 作業の後に Unity の batch が終了しないことがある（スレッド 1 本で CPU を使い続ける）。OSM を含まない最小の project でも出た。

測っていないこと

Player の build、別の PC・Library、実データ（SampleGame）、prefab variant・override を持つ instance・unpack した prefab、入れ子の prefab での印の方式、複数の Scene、build が途中で落ちた時の扱い、BuildContentOptions.CleanBuildCache が CleanBuildCache() と同じ効果か、cache を消した build の所要。
