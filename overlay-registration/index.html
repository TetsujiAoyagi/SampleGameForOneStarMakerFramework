取得した build に、手元で build した上書きを重ねて登録する

Unity 6000.6 の Content Directory で、CI から取得した build（base）に、開発者が自分の触った Scene と asset だけを build した上書きを後から登録し、Editor の Play で何が読まれるかを実測した記録です。対象は OneStarMaker（OSM）の開発時の Play の形です。

範囲: 1 台の PC、Unity 6000.6.0f1、StandaloneWindows64、loose file（非圧縮）、Editor の Play（Domain Reload 無効）、base と上書きを同じ Library で build、合成 fixture 1 つ。Player・別の PC で build した base・実データでは測っていません。「実体の数」は load の結果として区別できる UnityEngine.Object の数（相異なる EntityId）です。

問い

OSM の当面の方針は「CI は目的ごとに 1 本の build を作る。開発者はそれを取得し、自分が触った物だけを手元で build して上書きとして登録する」です。この形では、編集した Scene・texture や、script をまとめた file が、同じ id で中身の違う fileとして base と上書きの両方に必ず入ります。前の記事で測ったのは、中身が同じ file だけでした。今回は中身が違う場合について、次の 4 つを問いました。

  1. Q1: 両方にある物は、上書き側が読まれるか。
  2. Q2: base だけの Scene・prefab と上書きの Scene の component に、正しい class と値が付くか（base と上書きは、使う script の顔ぶれが違う）。
  3. Q3: 同じ asset の実体が、base の 1 つと上書きの 1 つに収まるか。
  4. Q4: 上書きを解除しない限り、Scene の出入りを繰り返しても Play の終わりまで壊れないか。

答え

base → 上書きの順で登録
YES
Q1〜Q4 が全て成立。編集した Scene と texture は上書きの版が出た
上書き → base の逆順
base の版
壊れはしないが、上書きが効かない
base の版を選ぶ手段
無し
2 つの root の Scene の id が等しく、どちらから要求しても同じ結果

どちらの順でも、後から登録した directory の版が出ました。登録も load も拒否されず、Warning も Error も出ていません。

問いbase → 上書き（主の順）上書き → base（対照）
Q1 編集した物の版上書き（v2）。base の root の id で要求しても v2base（v1）。どちらの root の id からも v1
Q2 class と値正しい。Missing 0正しい。ただし載ったのは base 版の Scene
Q3 共通 asset の実体各 2（base と上書きに 1 つずつ）各 1
Q4 Scene の出入り無傷。load し直しても上書きの版のまま（主の順だけで測った）

見落としやすい 1 点: Scene の直接参照は古い版のまま

base だけにある Scene SceneKeep の Renderer が直接参照している、編集した texture EditedTex は、上書きを登録した後も base の版（v1）でした。同じ Play の中で、上書きの Scene には新しい texture が、base の Scene には古い texture が出ます。

これは前の記事で立てた推測（Scene の直接参照は、その Scene のある directory の中で解決される）と合います。つまり、共通の asset を編集したら、それを直接参照している Scene も上書きに入れる必要があります。どの Scene を入れるべきかを、編集した asset から逆引きする道具が要ります。

設計への含意

  • 「取得した build 1 つ + 手元の上書き」は、開発時の Play の形の候補にできる。
  • 製品は、登録の順を base → 上書きに固定する。逆の順では上書きが効かない。
  • 上書きを登録している間、同じ id の物について base の版は選べない。base の版が要るなら上書きを解除する。これを製品の既定の制約として受け入れた。
  • 上書きに入れる Scene を、編集した asset から逆引きする道具は、次のスライス（目的 build を選ぶ索引と、上書きの登録契約）に含める。

途中で分かった副産物

test 用の asmdef に置いた component の script は、build に入りませんでした。 最初は probe の MonoBehaviour を、UNITY_INCLUDE_TESTS を制約に持つ test 支援の assembly に置き、build にその define を渡していました。すると Unity の入力 package の test 用 code まで compile の対象になり、base の build が error CS0117 で失敗しました。一方、define を渡さなければ、probe が player の script の compile に入りません。最終的に probe を test 制約の無い専用の asmdef へ移して解決しました。Content Directory の build を伴う実験では、component の script の置き場所に注意が要ります。

どう測ったか

  • SampleGame を使わない fixture を固定 GUID で生成した。source が v1 の状態で全体を build したものを base とし、source を v2 に変えてから SceneEdit と EditedTex の root だけを build したものを上書きとした。
  • 登録の前に、危険な条件が fixture に本当に入っていることを確かめた。script をまとめた file は、base と上書きで同じ id・違う sha256 で、base は base だけの script を、上書きは上書きだけの script を持つ。これが成り立たなければ未判定にする。
  • 製品の native wrapper（UnityContentDirectoryBackend）を無改変で 2 つ持ち、両方を登録してから load した。class は、component の位置ごとに完全名と値で照合した。
  • Domain Reload 無効の Play では、前の Play が読んだ物が残りうる。そこで、最初の Play だけが違う Unity process を 5 つ用意し、各観測の答えは、それが process の最初の Play になった回から採った。5 つの process の答えは全て一致した。
  • テストの合格は「harness が最後まで動いた」ことしか意味しない。答えは record（JSONL）の観測の行から、事前に凍結した定義で読んだ。別ベンダーのモデルによる独立監査と外部レビューも、同じ答えを出した。

測っていないこと

Player、別の PC・Library で build した base、実データ（SampleGame）、archive、3 つ以上の directory、上書きが 2 つ以上の時、上書きで script の code や field を変えた時、URP の Lit の variant、Scene に置いた prefab instance・nested prefab・sprite atlas・audio、Domain Reload 有効の Play、Scene を load した後に上書きを登録する順、Play の途中の上書きの解除、GPU 側の資源の重複。
